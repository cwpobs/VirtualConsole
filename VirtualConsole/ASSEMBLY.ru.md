# Virtual Console Assembly Language

Документация ассемблера виртуального процессора.

Документ будет дополняться по мере развития виртуальной машины.

---

# 1. Общая информация

Виртуальный процессор 8-битный: регистры общего назначения,
АЛУ и шина данных оперируют байтами. Адресация памяти при
этом 32-битная — адреса и указатели (`PC`/`SP`/`HL`) занимают
4 байта, что позволяет в будущем расширять память практически
неограниченно, не меняя формат команд.

Размер оперативной памяти:

    4 МБ (4 * 1024 * 1024 байт)

Карта адресного пространства:

| Диапазон | Назначение |
|----------|------------|
| `0x00000000 - 0x003FFFFF` | RAM (4 МБ) |
| `0xF0000000` и выше | MMIO-устройства (см. раздел 9) |

MMIO специально вынесено далеко от RAM — между ними огромный
запас адресов, так что RAM можно расширять в будущем, не
трогая и не переезжая устройства.

## Устройства - сводка

Подключённые к шине устройства (подробности по каждому - раздел 9):

| Устройство | Диапазон | Размер | Назначение |
|---|---|---|---|
| Timer | `0xF0000000-0xF0000004` | 5 Б | такты, прерывание по таймеру |
| Keyboard | `0xF0000005-0xF0000006` | 2 Б | очередь нажатий, прерывание |
| Text VRAM | `0xF0000007-0xF00007D8` | 2002 Б | текст 80x25, кодировка CP866 |
| DebugPort | `0xF00007D9-0xF00007E5` | 13 Б | `PC`/`SP`/`HL`/`FLAGS`, только чтение |
| Disk C | `0xF00007E6-0xF00007F8` | 19 Б | файловая система (папка `C/` на хосте) |
| Disk D | `0xF00007F9-0xF000080B` | 19 Б | файловая система (папка `D/` на хосте) |
| TextAttr | `0xF000080C-0xF0000FDD` | 2002 Б | цвет символов 80x25 (fg/bg) |
| VideoCard | `0xF0000FDE-0xF0000FFB` | 30 Б | графика 320x240, спрайты, тайлы |
| Clock | `0xF0000FFC-0xF0000FFD` | 2 Б | часы реального времени (мс) |
| ConsoleLayer | `0xF0001042` | 1 Б | видимость текстового слоя поверх VideoCard |
| PngLoader | `0xF0000FFE-0xF0001011` | 20 Б | загрузка PNG (спрайты/тайлы) |
| MapLoader | `0xF0001012-0xF000101F` | 14 Б | загрузка текстовой карты тайлов |
| ModLoader | `0xF0001020-0xF0001041` | 34 Б | загрузка `.mod`-музыки (ProTracker) |
| SoundCard | `0xF0001066-0xF000106E` | 9 Б | воспроизведение (PLAY/STOP/VOLUME) + визуализация (громкость каналов/ROW/ORDER_POS) |
| Mouse | `0xF0001075-0xF000107A` | 6 Б | относительное перемещение мыши (знак+модуль), кнопки, захват |
| MatrixLoader | `0xF000108D-0xF00010A3` | 23 Б | загрузка произвольной матрицы чисел (карта уровня и т.п.) с обратным чтением ячеек |
| Gpu3D | `0xF0001100-0xF00011FF` | 256 Б | 3D-ускоритель + освещение + математический сопроцессор 16/32 бита (вершины/треугольники/кубы/PRESENT) |
| Phys3D | `0xF0001200-0xF00012FF` | 256 Б | физический ускоритель: гравитация, AABB-коллизии, бесконечная плоскость пола |
| KeyState | `0xF0001300` | 1 Б | какие стрелки зажаты прямо сейчас |

Тактовой частоты у CPU нет как таковой — это программный интерпретатор
(`CPU::step()`), а не настоящая электронная схема, поэтому "скорость"
целиком зависит от хост-машины и не гарантируется. Для ориентира: в
ходе разработки headless-тесты этого же проекта показывали пропускную
способность порядка ~6 млн `step()`/сек на разработческой машине — это
не спецификация, а просто наблюдение, полезное для оценки, сколько
шагов заложить в собственный тест.

Экран и клавиатура по умолчанию — не окно консоли Windows, а
собственное графическое окно VM, **видеоконсоль** (`VideoConsole`):
битмап-шрифт CP866 8x16, зашитый в код (никаких файлов шрифта на
диске), и то же самое окно, в котором рисует `VideoCard` (см. её
раздел ниже) — текст и графика делят один общий экран, а не два
раздельных окна. Выбирается настройкой `console` в `config.txt`
(`video` по умолчанию, `text` — резервный текстовый режим, обычное
окно консоли Windows с ANSI-выводом и вводом через `_getch()`, вход/
выход CP866, см. `main.cpp`/`VmConfig.cpp`); в текстовом режиме у
`VideoCard` нет своего экрана вообще — графика в нём недоступна.

# 2. Регистры

Процессор имеет четыре основных 8-битных регистра:

    A
    B
    C
    D

Также существуют специальные регистры:

    PC      Program Counter
    SP      Stack Pointer
    FLAGS   Flags Register


## A, B, C, D

Универсальные 8-битные регистры.

Диапазон:

    0 - 255

Пример:

    LDI A, 100
    LDI B, 20


## PC

Program Counter.

32-битный адрес следующей выполняемой инструкции.

После обычного выполнения инструкции PC
автоматически увеличивается.

Инструкции перехода могут изменить PC.


## SP

Stack Pointer.

32-битный. Указывает на следующий свободный байт стека.

Стек растёт вниз (от старших адресов к младшим) и
занимает верхнюю часть RAM.

Текущая начальная позиция:

    0x003FFFFF (последний байт RAM)

`PUSH register`:

    Записать register по адресу SP, затем SP--

`POP register`:

    SP++, затем прочитать register по адресу SP


## HL

Регистр-указатель для косвенной адресации.

32-битный, используется инструкциями `STX`/`LDX` как
адрес в памяти. Позволяет обращаться к памяти по адресу,
вычисленному во время выполнения программы (а не зашитому
в саму инструкцию, как у `LDA`/`STA`) — например, для
последовательной записи символов в `Text VRAM`.

Начальное значение:

    0x00000000


## FLAGS

Регистр флагов.

Текущие флаги:

    Bit 0 - ZERO
    Bit 1 - CARRY

ZERO устанавливается инструкцией `CMP`, если значения равны.

CARRY - флаг переноса/заёма, нужен для многобайтовой арифметики
(складывать/вычитать числа шире одного байта) и для сравнения
"меньше/больше" (в дополнение к "равно" у `ZERO`):

- `ADD`/`ADC`: `CARRY=1`, если сумма превысила 255 (было переполнение).
- `SUB`/`SBC`: `CARRY=1`, если потребовался заём (`A` было меньше
  вычитаемого).
- `CMP`: `CARRY=1`, если `A < register` (без изменения `A`).

Например, после `CMP B`: `ZERO=1` значит `A == B`; `CARRY=1` значит
`A < B`; оба сброшены - значит `A > B`. Так получается полноценное
беззнаковое сравнение "меньше/больше/равно", а не только "равно".

# 3. Инструкции

## LDI

Load Immediate.

Загрузить непосредственное значение в регистр.

Синтаксис:

    LDI register, value

Примеры:

    LDI A, 10
    LDI B, 255
    LDI C, 0xFF

Машинный формат:

    01 register value

Коды регистров:

    A = 0
    B = 1
    C = 2
    D = 3

Пример:

    LDI A, 10

Машинный код:

    01 00 0A


---

## LDA

Load A.

Загрузить значение из памяти в регистр A.

Синтаксис:

    LDA address

Пример:

    LDA 1000

или:

    LDA 0x03E8

Машинный формат:

    02 b0 b1 b2 b3

Адрес — 32-битный, 4 байта little-endian
(`b0` — младший байт, `b3` — старший).


---

## STA

Store A.

Записать содержимое регистра A в память.

Синтаксис:

    STA address

Пример:

    STA 1000

Машинный формат:

    03 b0 b1 b2 b3

Адрес — 32-битный, 4 байта little-endian.


---

## ADD

Прибавить значение регистра к A.

Синтаксис:

    ADD register

Примеры:

    ADD B
    ADD C

Эквивалент:

    A = A + register

Устанавливает флаг CARRY, если сумма превысила 255 (сбрасывает
иначе) - см. `ADC` для сложения с переносом (многобайтовые числа).
Флаг ZERO не трогает.

Машинный формат:

    04 register


---

## SUB

Вычесть значение регистра из A.

Синтаксис:

    SUB register

Примеры:

    SUB B
    SUB C

Эквивалент:

    A = A - register

Устанавливает флаг CARRY, если потребовался заём (`A < register`),
сбрасывает иначе - см. `SBC` для вычитания с заёмом (многобайтовые
числа). Флаг ZERO не трогает.

Машинный формат:

    05 register


---

## ADC

Прибавить значение регистра и флаг CARRY к A ("add with carry").

Синтаксис:

    ADC register

Эквивалент:

    A = A + register + CARRY

Обновляет CARRY так же, как `ADD`. Нужен для сложения чисел шире
одного байта: сложить младшие байты через `ADD` (перенос попадёт в
CARRY), затем старшие байты через `ADC` (учтёт этот перенос).

Пример сложения двух 16-битных чисел (`A:C` = `A1:C1` + `A2:C2`,
младший байт в `C`, старший в `A`):

    LDI A, 244   ; младший байт первого числа
    LDI B, 50    ; младший байт второго числа
    ADD B        ; A = сумма младших байт, CARRY = был ли перенос
    PUSH A
    POP C        ; C = младший байт результата

    LDI A, 1     ; старший байт первого числа
    LDI B, 0     ; старший байт второго числа
    ADC B        ; A = сумма старших байт + перенос из ADD выше

Машинный формат:

    1F register


---

## SBC

Вычесть значение регистра и флаг CARRY из A ("subtract with borrow").

Синтаксис:

    SBC register

Эквивалент:

    A = A - register - CARRY

Обновляет CARRY так же, как `SUB`. Симметричен `ADC` - используется
для вычитания многобайтовых чисел (сначала `SUB` на младших байтах,
затем `SBC` на старших).

Машинный формат:

    20 register


---

## CMP

Сравнить A с другим регистром.

Синтаксис:

    CMP register

Пример:

    CMP B

Если:

    A == B

устанавливается флаг ZERO (и сбрасывается иначе).

Дополнительно устанавливает флаг CARRY, если `A < B` (и сбрасывает
иначе) - см. раздел "2. Регистры" (FLAGS) про полноценное
беззнаковое сравнение через ZERO+CARRY.

Машинный формат:

    06 register


---

## MUL

Умножить A на значение регистра.

Синтаксис:

    MUL register

Примеры:

    MUL B
    MUL C

Эквивалент:

    A = A * register

Результат обрезается до 8 бит (как и переполнение `ADD`/`SUB`) —
`A` и `register` оба 8-битные, а их произведение может доходить
до 65025, что не помещается в один байт. Для подсчёта очков или
других величин, которым может понадобиться больше 8 бит, нужно
самостоятельно хранить результат в нескольких байтах.

Машинный формат:

    16 register


---

## DIV

Разделить A на значение регистра (целочисленное деление).

Синтаксис:

    DIV register

Примеры:

    DIV B
    DIV C

Эквивалент:

    A = A / register

Деление на 0 — безопасный no-op: `A` остаётся без изменений
(вместо неопределённого поведения или аварийного завершения).

Машинный формат:

    17 register


---

## MOD

Остаток от деления A на значение регистра.

Синтаксис:

    MOD register

Примеры:

    MOD B
    MOD C

Эквивалент:

    A = A % register

Деление на 0 — безопасный no-op: `A` остаётся без изменений.

Машинный формат:

    18 register

`DIV`/`MOD` вместе позволяют получить и частное, и остаток от
одного и того же числа — например, для перевода числа в
десятичный текст (см. подпрограмму `print_number` в `boot.asm`).

## NOT

Побитовое отрицание A (все биты инвертируются).

Синтаксис:

    NOT

Эквивалент:

    A = ~A

Машинный код:

---

## SHL

Shift Left. Сдвигает A на 1 бит влево, старший бит теряется,
младший заполняется нулём.

Синтаксис:

    SHL

Эквивалент:

    A = A << 1

Машинный код:

    1D


---

## SHR

Shift Right. Сдвигает A на 1 бит вправо (логический сдвиг),
младший бит теряется, старший заполняется нулём.

Синтаксис:

    SHR

Эквивалент:

    A = A >> 1

Машинный код:

    1E

`AND`/`OR`/`XOR`/`NOT`/`SHL`/`SHR`, как и остальные арифметические
инструкции (`ADD`/`SUB`/`MUL`/`DIV`/`MOD`), не изменяют `FLAGS` —
флаг `ZERO` по-прежнему выставляет только `CMP`.

## POP

Снять значение со стека в регистр.

    POP register

## CALL

Вызвать подпрограмму.

Кладёт на стек адрес возврата (адрес инструкции,
следующей за CALL, 4 байта), затем переходит по указанному
адресу.

Синтаксис:

    CALL address

Пример:

    CALL subroutine

Можно использовать метку:

    CALL setD

Машинный формат:

    0C b0 b1 b2 b3


---

## RET

Вернуться из подпрограммы.

Снимает со стека адрес возврата (4 байта), положенный туда
инструкцией CALL, и переходит по нему.

Синтаксис:

    RET

Машинный код:

    0D

Пример вызова и возврата подпрограммы:

    CALL setD

    HLT

setD:

    LDI D, 123
    RET


---

Синтаксис:

    EI

Машинный код:

## DI

## RETI

Return from Interrupt.

Вернуться из обработчика прерывания: снимает со стека

Синтаксис:

    RETI

Машинный код:

    10

обработчика.

## INCHL

Increment HL.

Увеличить HL на 1.

Синтаксис:

    INCHL

Машинный код:

    14

Пример: последовательная запись двух символов в Text VRAM
без указания адреса каждой ячейки вручную:

    LDHL 0xF0000007

    LDI A, 72
    STX             ; VRAM[0xF0000007] = 'H'
    INCHL

    LDI A, 105
    STX             ; VRAM[0xF0000008] = 'i'
    INCHL

## ADDHL

Add to HL (16-bit).

Прибавить к HL 16-битное значение, собранное из пары
регистров: `HL += (regHigh << 8) | regLow`. В отличие от
`INCHL` (сдвиг на 1 за шаг), это сдвиг на произвольное
runtime-смещение за ОДИН шаг — нужен, когда смещение
заранее не известно и может быть большим (индекс массива,
координата на экране `y*80+x` и т.п.), а гонять `INCHL` в
цикле по нему слишком дорого.

Синтаксис:

    ADDHL regHigh, regLow

Машинный код:

    23 <regHigh> <regLow>

где `<regHigh>`/`<regLow>` — код регистра (A=0, B=1, C=2,
D=3), как в `LDI`.

Пример: сдвинуть HL на 300 (`0x012C` = старший байт 1,
младший 44), используя пару регистров B/C:

    LDHL 0xF0000007

    LDI B, 1
    LDI C, 44
    ADDHL B, C      ; HL = 0xF0000007 + 300

Именно на этой инструкции построены `__mc_hladd` и
`__mc_screen_offset` в Мини-C — компилятор считает нужное
смещение в паре регистров обычным `ADD`/`ADC` (см. "Пример:
сложение многобайтовых чисел" выше) и одним `ADDHL`
применяет его к `HL`, вместо цикла из сотен/тысяч `INCHL`.

## DB

Define Byte.

Резервирует один байт данных со значением `value`. Это
псевдо-инструкция — не опкод процессора, а указание
ассемблеру зарезервировать байт памяти прямо в потоке
кода, обычно под меткой.

Синтаксис:

    label: DB value

Пример:

    quit: DB 0

Адрес такой переменной вычисляется тем же счётчиком
адреса, что и адреса инструкций, — значит `DB` физически
не может наложиться на код. Это единственный способ в
этом ассемблере резервировать данные, не подбирая адрес
вручную (см. также раздел "4. Метки" ниже).

**Важно**: `DB`, как и метки подпрограмм, нужно размещать
там, где до него не доходит обычное выполнение (обычно —
в конце файла, после последнего `HLT`/`RETI`), иначе
процессор попытается исполнить этот байт как опкод.

# 4. Метки

Метки позволяют обращаться к адресам программы
по имени.

Синтаксис:

    label:

Пример:

    loop:
        JMP loop


Метки можно использовать в инструкциях перехода:

    JMP loop
    JZ success
    JNZ loop


Пример:

    LDI A, 10

loop:

    SUB B
    CMP C

    JNZ loop

    HLT


Ассемблер автоматически заменяет имя метки
на соответствующий адрес.


## Данные под меткой (DB)

Метка перед `DB` даёт переменной имя вместо адреса:

    quit: DB 0
    ...
    STA quit
    LDA quit

`LDA`/`STA` (как и `JMP`/`CALL`) принимают и метку, и
голый адрес — использовать имя удобнее и безопаснее: адрес
вычисляет ассемблер, вручную подбирать его не нужно.

**Почему это важно.** У этого ассемблера нет разделения
кода и данных (нет `ORG`, нет секций) — все байты, включая
`DB`, ложатся в общий, последовательно растущий поток
адресов. Если задать адрес переменной вручную (например,
`STA 0x0102`) и программа потом вырастет настолько, что
код дойдёт до этого адреса, запись в переменную начнёт
затирать собственный исполняемый код программы — с трудно
диагностируемыми последствиями (выполнение "уезжает" в
случайное место). Использование `DB` полностью исключает
этот класс ошибок: адрес переменной всегда считается тем же
счётчиком, что и адреса инструкций, поэтому наложение
структурно невозможно.

Явно захардкоженный адрес переменной оправдан только тогда,
когда к нему обращается код *вне* этой программы — например,
`main.cpp` читает через `Bus` фиксированные адреса
`0x00010000`/`0x00010001`/`0x00010002`/`0x00010003` для отрисовки и
диагностики (см. `boot.asm`). Раз `main.cpp` не видит меток
ассемблера, такие "интерфейсные" адреса приходится фиксировать
вручную и держать достаточно далеко от возможного роста кода.

**Реальный случай**: изначально эти адреса были на `0x00001000`
(4096). Когда `boot.asm` подрос до ~4.6 КБ (добавились команды
`dir`/`type`/`cd`), код дорос до этой границы, и `boot.asm` начал
сам себя затирать записью в "интерфейсные" адреса — терминал
переставал рисовать баннер без единой ошибки ассемблера (нашли
диагностикой размера `machineCode.size()`). Адреса перенесены на
`0x00010000` (65536) с большим запасом.

# 9. Устройства на шине (Memory-Mapped I/O)

Помимо оперативной памяти, к процессору через шину (Bus)
могут быть подключены другие устройства. Каждое устройство
занимает свой диапазон адресов.

Текущая карта адресного пространства:

| Диапазон адресов | Устройство |
|-------------------|------------|
| 0x00000000 - 0x003FFFFF | Memory (RAM, 4 МБ) |
| 0xF0000000 - 0xF0000004 | Timer |
| 0xF0000005 - 0xF0000006 | Keyboard |
| 0xF0000007 - 0xF00007D8 | Text VRAM (сетка + SCROLL + CLEAR) |
| 0xF00007D9 - 0xF00007E5 | DebugPort (PC/SP/HL/FLAGS, только чтение) |
| 0xF00007E6 - 0xF00007F8 | Disk C (папка "C" рядом с exe) |
| 0xF00007F9 - 0xF000080B | Disk D (папка "D" рядом с exe) |
| 0xF000080C - 0xF0000FDD | TextAttr (цвет символа/фона + SCROLL + CLEAR) |
| 0xF0000FDE - 0xF0000FFB | VideoCard (растровый режим 320x240, 16 спрайтов, тайлы+скролл) |
| 0xF0000FFC - 0xF0000FFD | Clock (часы реального времени, std::chrono) |
| 0xF0000FFE - 0xF0001011 | PngLoader (декодирование PNG в спрайты/тайлы) |
| 0xF0001012 - 0xF000101F | MapLoader (текстовая карта тайлов) |
| 0xF0001020 - 0xF0001041 | ModLoader (разбор .mod-файлов) |
| 0xF0001042 | ConsoleLayer (видимость текстового слоя поверх VideoCard) |
| 0xF0001043 | ModLoaderDiskSelect (явный выбор диска для ModLoader - см. "ModLoader") |
| 0xF0001044 - 0xF0001065 | неиспользуемая дыра (старые места SoundCard/Gpu3D - Gpu3D переехал, чтобы освободить место под слияние с Light3D/MathUnit, см. ниже) |
| 0xF0001066 - 0xF0001074 | SoundCard (PLAY/STOP/PAUSE/RESUME, VOLUME, визуализация, запрос ячейки паттерна PATTERN_*) |
| 0xF0001075 - 0xF000107A | Mouse (относительное перемещение знак+модуль, кнопки, захват) |
| 0xF000107B - 0xF000108C | неиспользуемая дыра (старые места MathUnit/Light3D - слиты в Gpu3D, см. ниже) |
| 0xF000108D - 0xF00010A3 | MatrixLoader (загрузка произвольной матрицы чисел с обратным чтением ячеек) |
| 0xF0001100 - 0xF00011FF | Gpu3D (3D-ускоритель + освещение + математический сопроцессор 16/32 бита - вершины/треугольники/кубы/PRESENT; зарезервировано 256 Б, используется ~97) |
| 0xF0001200 - 0xF00012FF | Phys3D (физический ускоритель: гравитация, AABB-коллизии, бесконечная плоскость пола; зарезервировано 256 Б, используется ~34) |
| 0xF0001300 | KeyState (какие стрелки зажаты прямо сейчас, 1 Б) |

MMIO вынесено далеко от RAM (на `0xF0000000`), а не сразу за
её текущим концом — так RAM можно будет расширять в будущем, не
трогая и не переезжая устройства. Диапазоны не пересекаются,
поэтому порядок регистрации устройств на шине не важен.

## Timer

Считает такты. Один такт происходит на каждое
обращение процессора к шине (чтение опкода, операнда
или доступ к памяти/устройству), а не на каждую
инструкцию.

Разные инструкции занимают разное число тактов, в
зависимости от того, сколько байт они читают/пишут:

| Инструкция | Тактов |
|------------|--------|
| LDI | 3 |
| LDA | 6 |
| STA | 6 |
| ADD | 2 |
| SUB | 2 |
| CMP | 2 |
| JMP | 5 |
| JZ | 5 |
| JNZ | 5 |
| PUSH | 3 |
| POP | 3 |
| CALL | 9 |
| RET | 5 |
| EI | 1 |
| DI | 1 |
| RETI | 6 |
| LDHL | 5 |
| STX | 2 |
| LDX | 2 |
| INCHL | 1 |
| DECHL | 1 |
| ADDHL | 3 |
| MUL | 2 |
| DIV | 2 |
| MOD | 2 |
| AND | 2 |
| OR | 2 |
| XOR | 2 |
| NOT | 1 |
| SHL | 1 |
| SHR | 1 |
| ADC | 2 |
| SBC | 2 |
| JC | 5 |
| JNC | 5 |
| HLT | 1 |

`LDA`/`STA`/`JMP`/`JZ`/`JNZ`/`CALL`/`LDHL` стали дороже, чем
были на 16-битной адресации (было `LDA/STA`=4, `JMP/JZ/JNZ/LDHL`=3,
`CALL`=5, `RET`=3, `RETI`=4) — адрес теперь 4 байта вместо 2.

Вход в прерывание (см. раздел 10) не является
инструкцией из ассемблера, но тоже стоит тактов:
5 тактов (запись 4 байт PC и 1 байта FLAGS на стек).

| Адрес | Регистр | Чтение | Запись |
|-------|---------|--------|--------|
| 0xF0000000 | COUNT_LOW | Младший байт счётчика | Сбрасывает счётчик в 0 |
| 0xF0000001 | COUNT_HIGH | Старший байт счётчика | Сбрасывает счётчик в 0 |
| 0xF0000002 | CMP_LOW | Младший байт порога сравнения | Устанавливает младший байт порога |
| 0xF0000003 | CMP_HIGH | Старший байт порога сравнения | Устанавливает старший байт порога |
| 0xF0000004 | CONTROL | Бит 0 = ENABLE, бит 1 = PENDING | Бит 0 записанного значения = ENABLE; любая запись сбрасывает PENDING |

Счётчик 16-битный (сам по себе, независимо от того, что
адресация теперь 32-битная). Когда таймер включён (`ENABLE=1`)
и счётчик достигает значения порога сравнения (`CMP`), он
сбрасывается в 0 и устанавливается флаг `PENDING` —
запрос прерывания (см. раздел 10). Порог `CMP = 0`
считается "выключено" (никогда не сработает), даже если
`ENABLE=1`.

Пример чтения значения таймера в регистр A:

    LDA 0xF0000000  ; младший байт таймера в A

Пример сброса счётчика таймера:

    STA 0xF0000000  ; любое значение сбрасывает счётчик

Пример настройки таймера на прерывание раз в 1000 тактов:

    LDI A, 0xE8
    STA 0xF0000002      ; CMP_LOW  = 0xE8
    LDI A, 0x03
    STA 0xF0000003      ; CMP_HIGH = 0x03   (0x03E8 = 1000)
    LDI A, 1
    STA 0xF0000004      ; ENABLE = 1


## Clock

Настоящие часы реального времени (`std::chrono::steady_clock`) - в
отличие от `Timer` выше (чей `counter` растёт на каждое обращение к
шине, а значит зависит от того, сколько шинных операций уходит на
кусок кода, а не от реального времени), `Clock` всегда отдаёт РЕАЛЬНО
прошедшие миллисекунды с момента последнего сброса, независимо от
скорости хоста и от того, как часто его опрашивают. Нужен там, где
важна настоящая, а не "тактовая", синхронизация - например, пауза
между кадрами анимации (см. `C/DEMOS/DEMO.ASM`).

| Адрес | Регистр | Чтение | Запись |
|-------|---------|--------|--------|
| 0xF0000FFC | MILLIS_LOW | Младший байт прошедших мс | Сбрасывает часы (обнуляет прошедшее время) |
| 0xF0000FFD | MILLIS_HIGH | Старший байт прошедших мс | Сбрасывает часы |

16-битное значение мс переполняется (оборачивается через 0) примерно
раз в 65 секунд - для пауз между кадрами (десятки миллисекунд) этого
с огромным запасом достаточно.

Пример - ждать ровно 60 кадров в секунду (~16.7 мс на кадр):

    LDI A, 0
    STA 0xF0000FFC      ; сброс часов

wait_frame:

    LDA 0xF0000FFD      ; MILLIS_HIGH - страховка на случай >255 мс
    LDI B, 0
    CMP B
    JNZ frame_done

    LDA 0xF0000FFC      ; MILLIS_LOW
    LDI B, 17
    CMP B
    JC wait_frame

frame_done:


## Keyboard

Читает реальные нажатия клавиш с консоли. Каждое
нажатие попадает в очередь (16 байт), откуда процессор
вычитывает их по одному через регистр DATA.

В очередь попадают нажатия НЕ только из окна консоли: пока открыто
графическое окно `VideoCard` (`MODE_ON`), оно само ловит нажатия
(`WM_CHAR`) и кладёт их в ту же очередь - иначе клавиатура "переставала
бы работать", стоило пользователю кликнуть по графическому окну и
забрать у консоли фокус ОС (`_kbhit()`/`_getch()`, которыми `Keyboard`
опрашивает консольный ввод, получают нажатия только пока фокус на
консоли). Для ассемблерной программы разницы нет - откуда бы ни пришло
нажатие, оно просто лежит в общей очереди.

| Адрес | Регистр | Чтение | Запись |
|-------|---------|--------|--------|
| 0xF0000005 | DATA | Снять и вернуть следующий байт из очереди (0, если очередь пуста) | Игнорируется |
| 0xF0000006 | CONTROL | Бит 0 = ENABLE, бит 1 = HAS_DATA (очередь не пуста) | Бит 0 записанного значения = ENABLE |

Если очередь переполнена (набрано более 16 непрочитанных
клавиш), новые нажатия теряются.

Прерывание клавиатуры — уровневое, а не защёлка: оно активно,
пока `ENABLE=1` и очередь не пуста, и само снимается, когда
обработчик вычитывает данные через `DATA` (в отличие от
`Timer`, здесь нет отдельного подтверждения записью в
`CONTROL`). Если во время обработки одного прерывания в
очередь попало ещё несколько клавиш, процессор сразу получит
следующее прерывание и обработает их один за другим.

Пример чтения кода нажатой клавиши в регистр A:

    LDA 0xF0000005

Пример включения прерываний от клавиатуры:

    LDI A, 1
    STA 0xF0000006      ; ENABLE = 1


## Text VRAM

Текстовый экран 80x25 символов (2000 байт) плюс регистр
`SCROLL`. Каждый байт сетки — один символ на экране. Адрес
ячейки:

    address = 0xF0000007 + y * 80 + x

где `x` — столбец (0-79), `y` — строка (0-24).

| Адрес | Регистр | Описание |
|-------|---------|----------|
| 0xF0000007 - 0xF00007D6 | сетка 80x25 | один байт на символ (ASCII) |
| 0xF00007D7 | SCROLL | запись любого значения сдвигает весь экран на одну строку вверх, последняя строка очищается |
| 0xF00007D8 | CLEAR | запись любого значения заполняет всю сетку пробелами |

Хранит один байт на символ (как классический текстовый режим
VGA) — поддерживаются только однобайтовые коды (ASCII), не
UTF-8. У сетки нет прерываний и регистров управления, кроме
`SCROLL` — обычный блок памяти, куда можно писать и откуда
можно читать через `LDA`/`STA`.

Пример вывода "Hi" в левый верхний угол экрана (фиксированные
адреса, без HL):

    LDI A, 72
    STA 0xF0000007      ; H
    LDI A, 105
    STA 0xF0000008      ; i

Для последовательного вывода (без вычисления адреса каждой
ячейки вручную) используется косвенная адресация через `HL`/
`STX`/`INCHL` — см. раздел "3. Инструкции". Пример:

    LDHL 0xF0000007

    LDI A, 72
    STX             ; VRAM[0xF0000007] = 'H'
    INCHL

    LDI A, 105
    STX             ; VRAM[0xF0000008] = 'i'
    INCHL

`HL` при этом не проверяется на выход за пределы сетки (2000
байт) — после 2000 записей курсор дойдёт до регистра `SCROLL`
и запись сдвинет экран, а не запишет символ. Готовый пример
переноса строки и прокрутки — подпрограмма `advance_row` в
`boot.asm`.


## DebugPort

Устройство только для чтения. Даёт программе доступ к тем
регистрам процессора, которые иначе прочитать в обычный регистр
нельзя — `PC`/`SP`/`HL`/`FLAGS` не связаны ни с одной инструкцией
чтения (в отличие от `A`/`B`/`C`/`D`, которые и так всегда доступны
программе напрямую).

| Адрес | Регистр | Описание |
|-------|---------|----------|
| 0xF00007D9 - 0xF00007DC | PC | 4 байта little-endian |
| 0xF00007DD - 0xF00007E0 | SP | 4 байта little-endian |
| 0xF00007E1 - 0xF00007E4 | HL | 4 байта little-endian |
| 0xF00007E5 | FLAGS | 1 байт |

Запись игнорируется. Используется командой `regs` в терминале
(`boot.asm`) для вывода состояния процессора.

Пример чтения младшего байта `PC`:

    LDA 0xF00007D9


## Disk

Устройство "диск" - физически папка на компьютере хоста (`C` или `D`
рядом с `VirtualConsole.exe`, создаются автоматически при старте).
Файлы разной длины не ложатся на модель "адрес=байт памяти", поэтому
это командный порт (регистры + команда-триггер), как `Timer`/
`Keyboard`, а не блок памяти вроде `Text VRAM`. Оба диска (`C`/`D`)
имеют одинаковый набор регистров по 19 байт, каждый на своём
диапазоне адресов.

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 0-11 | NAME | Имя файла, ASCII, до 12 символов, дополняется нулём |
| 12 | COMMAND (запись) | `1`=LIST_FIRST, `2`=LIST_NEXT, `3`=OPEN_READ, `4`=READ_BYTE, `5`=OPEN_WRITE, `6`=WRITE_BYTE, `7`=CLOSE, `8`=LOAD, `9`=DELETE, `10`=LOAD_SHELL, `11`=CHDIR, `12`=CHDIR_UP, `13`=LOAD_RAW, `14`=BUILD, `15`-`18`=LOAD_CHILD (уровни 2-5), `19`=MKDIR |
| 13 | STATUS (чтение) | `0`=OK, `1`=EOF/файлов больше нет, `2`=ошибка |
| 14 | DATA | Чтение - байт после `READ_BYTE`; запись - байт для `WRITE_BYTE` |
| 15-18 | SIZE (чтение) | Размер открытого файла, 4 байта little-endian (валиден после `OPEN_READ`) |

Диск C: адреса `0xF00007E6` (NAME0) - `0xF00007F8` (SIZE3).
Диск D: адреса `0xF00007F9` (NAME0) - `0xF000080B` (SIZE3).

Поддерживается произвольная глубина вложенности: `CHDIR` (`11`)
заходит в папку `NAME` (`STATUS=2`, если такой папки нет), `CHDIR_UP`
(`12`) поднимается РОВНО НА ОДИН уровень выше (не сразу в корень - на
корне тихо ничего не делает, как в DOS) - обе меняют "текущую папку"
диска (`currentDir` - `std::filesystem::path`, сам компонует путь
любой глубины), от которой дальше резолвятся ВСЕ файловые команды
(`LIST_FIRST`/`OPEN_READ`/`LOAD`/... - именно поэтому `dir`/`type`/
`exec` в терминале начинают показывать/находить файлы внутри папки
сразу после `cd`). Ограничение по глубине есть только в промпте
`SHELL.ASM` (`DIR_MAX_DEPTH = 8` - под стек имён папок для отображения
`C:\A\B\...>`) - у самого `Disk` его нет. `LIST_FIRST`/`LIST_NEXT`
перечисляют и файлы, и папки вперемешку - имя папки в `NAME`
дополнено хвостовым `/`, чтобы отличить её от обычного файла.

`LIST_FIRST`/`LIST_NEXT` перебирают файлы в папке: кладут имя
очередного файла в NAME и `STATUS=0`, либо `STATUS=1`, когда файлы
кончились.

Пример перечисления файлов на диске C:

    LDI A, 1
    STA 0xF00007F2      ; DiskC COMMAND = LIST_FIRST

    list_loop:
        LDA 0xF00007F3      ; DiskC STATUS
        LDI B, 1
        CMP B
        JZ list_done        ; файлов больше нет

        ; ...напечатать NAME0..NAME11 (0xF00007E6..0xF00007F1)...

        LDI A, 2
        STA 0xF00007F2      ; DiskC COMMAND = LIST_NEXT
        JMP list_loop
    list_done:

Пример чтения файла целиком (имя уже записано в NAME0-11):

    LDI A, 3
    STA 0xF00007F2      ; COMMAND = OPEN_READ

    read_loop:
        LDI A, 4
        STA 0xF00007F2      ; COMMAND = READ_BYTE
        LDA 0xF00007F3      ; STATUS
        LDI B, 1
        CMP B
        JZ read_done        ; EOF
        LDA 0xF00007F4      ; DATA - очередной байт файла
        ; ...что-то сделать с байтом...
        JMP read_loop
    read_done:
        LDI A, 7
        STA 0xF00007F2      ; COMMAND = CLOSE

Запись файла аналогична: записать байт в DATA, затем `COMMAND` =
`WRITE_BYTE` (`6`) - после `OPEN_WRITE` (`5`), который создаёт файл
(или обрезает существующий до 0 байт).

Готовые примеры использования - команды `dir`/`type` в терминале
(`boot.asm`).

`LOAD` (`8`) - особая команда: читает `NAME` **как текстовый
`.asm`-файл** (не как двоичные данные), собирает его тем же
ассемблером, что и `main.cpp` использует для `boot.asm`, и
записывает результат в RAM по фиксированному адресу `0x00002000` (та
же "песочница", что уже использует `poke`/`run`). `STATUS=0` при
успехе (`SIZE` - количество собранных байт), `STATUS=2` при ошибке
(файл не найден или ошибка ассемблера - без детализации причины).
Запускается затем обычным `CALL 0x00002000`, как код, записанный
через `poke`. Ассемблировать на самом процессоре (в 8-битной
программе) нереально - парсинг текста и генерация кода делает хост
(`Disk` держит собственный `Assembler` и указатель на `Bus`). Готовый
пример использования - команда `exec` в терминале (`boot.asm`).

Диск, с которого реально пришёл последний успешный `LOAD` в песочницу
`0x00002000` (то есть последний `exec`, НЕ `LOAD_SHELL`), запоминается
в `Disk::lastExecDisk` - статическом указателе, общем сразу для обоих
экземпляров `Disk` (C и D). Этим пользуются `PngLoader`/`MapLoader`/
`ModLoader` (см. соответствующие разделы ниже), чтобы резолвить СВОИ
ресурсы (PNG/карты/`.mod`) относительно того же диска, с которого была
запущена текущая программа, а не всегда с диска C - так одну и ту же
программу с ресурсами можно запускать что с `C:`, что с `D:`.

`LOAD_SHELL` (`10`) - то же самое, что `LOAD`, но кладёт результат по
адресу `0x00020000` (резидентное место `SHELL.ASM`, отдельное от
песочницы `poke`/`run`/`exec` - иначе они бы затирали код самого
шелла) и НЕ трогает `lastExecDisk` (это загрузка самой "операционной
системы" при старте VM, а не пользовательской программы).

Зазор между песочницей (`0x00002000`) и резидентным `SHELL.ASM`
(`0x00020000`) - это весь допустимый размер exec'нутой программы
(~120 КиБ) - `LOAD_RAW`/`LOAD` не проверяют размер файла, при
превышении хвост программы затрёт начало работающего `SHELL.ASM`
прямо во время исполнения. На практике места с большим запасом
хватает даже для больших программ на мини-C (см. ниже) - но это
жёсткая граница, а не мягкое ограничение.

`DELETE` (`9`) - удаляет файл `NAME` (`std::filesystem::remove`) -
тем же вызовом прекрасно удаляет и ПУСТУЮ папку (одна и та же команда
на оба случая; непустую папку просто отказывается удалять - никакого
рекурсивного удаления нет). `STATUS=0` при успехе, `STATUS=2`, если
файла/папки не было, папка оказалась не пуста, или удалить не
получилось. Готовые примеры использования - команда `del` в терминале
и `F8` в `C/TOOLS/FM.MC` (сначала диалог подтверждения Y/N - см.
`request_delete()`).

`MKDIR` (`19`) - создаёт новую пустую папку `NAME` в текущей папке
(`std::filesystem::create_directory`). `STATUS=0` при успехе,
`STATUS=2`, если файл/папка с таким именем уже есть или имя
некорректно. В отличие от остальных команд здесь - пока нет команды
`mkdir` в терминале `SHELL.ASM` - единственный готовый пример
использования - `F7` в `C/TOOLS/FM.MC` (спрашивает имя в маленьком
окошке ввода, затем шлёт `MKDIR` - см. `request_mkdir()`).

`BUILD` (`14`) - как `LOAD`, но результат ассемблирования пишется НЕ в
RAM, а в новый файл на диске: то же имя, что `NAME`, но расширение
заменено на `.RUN` (`ИМЯ.ASM` -> `ИМЯ.RUN`; если расширения не было -
просто дописывается `.RUN`). `STATUS=0` при успехе (`SIZE` - сколько
байт записано ВСЕГО, заголовок + код, см. ниже), `STATUS=2` при ошибке
(исходник не найден, ошибка ассемблера, не удалось создать выходной
файл). Готовый пример использования - команда `build` в терминале.

`ИМЯ.RUN` - не просто голый машинный код: файл начинается с заголовка -
таблицы релокаций (см. `Assembler::assemble()`, третий необязательный
параметр `relocations`, и `Disk::readRunFile()`): 4 байта - количество
смещений (`uint32` LE), затем сами смещения по 4 байта (`uint32` LE)
каждое, ОТНОСИТЕЛЬНО НАЧАЛА КОДА (то есть уже после заголовка). Каждое
смещение указывает на 4-байтный адрес, который ассемблер получил из
МЕТКИ (`JMP`/`CALL`/`LDA`/`STA`/`LDHL` на свою же метку/переменную
программы), а не из числового литерала - такие вроде `STA 0xF00007D8`
(абсолютные адреса устройств) в таблицу не попадают, они не зависят от
того, где лежит сама программа, сдвигать их нельзя. Сразу за таблицей -
собственно машинный код. Заголовок нужен, чтобы этот `.RUN` можно было
безопасно запустить НЕ там, где он собран - см. `LOAD_CHILD` ниже; для
обычного запуска (`LOAD_RAW`, тот же адрес, для которого собран)
заголовок просто пропускается.

`LOAD_RAW` (`13`) - читает `ИМЯ.RUN` (заголовок + код, см. `BUILD`
выше), пропускает заголовок (релокация не нужна - грузит туда же, для
чего собран, `0x00002000`, та же песочница, что и `LOAD`) и копирует
ТОЛЬКО код в RAM по этому адресу. `STATUS` аналогично `LOAD`; `SIZE` -
размер только кода (без заголовка), в отличие от `SIZE` у `BUILD`. Как
и `LOAD`, обновляет `Disk::lastExecDisk` - программа, запущенная из
`.RUN`, тоже резолвит свои PNG/карты/`.mod` относительно правильного
диска. Готовый пример использования - автозапуск `ИМЯ.RUN` по одному
имени в терминале (см. `cmd_autorun` в `SHELL.ASM`) - набранное на
приглашении имя, не совпавшее ни с одной известной командой,
пробуется как `ИМЯ.RUN` через `LOAD_RAW`, и при успехе запускается
точно так же, как `exec` - без явной команды, как `.exe`/`.com` в DOS.

`LOAD_CHILD` (`15`-`18`, по одной команде на каждый уровень
вложенности - см. "Запуск дочерней программы: exec_child()" в разделе
"Мини-C") - запускает уже готовый `ИМЯ.RUN` (собранный `BUILD` под
`0x00002000`) ИЗНУТРИ уже выполняющейся программы (а не из шелла), по
ОТДЕЛЬНОМУ адресу для каждого уровня (`Disk::EXEC_CHILD_DEPTH2..5_ADDRESS`
- `0x00100000`/`0x00140000`/`0x00180000`/`0x001C0000`). Нужна, потому
что сама выполняющаяся программа (например, файловый менеджер `FM.MC`)
живёт по адресу `0x00002000` - если бы дочернюю программу грузили туда
же, загрузка затёрла бы код, который в этот момент как раз исполняется,
а если бы у ВСЕХ уровней вложенности был один и тот же адрес - второй
уровень точно так же затёр бы первый.

В отличие от `LOAD_RAW`, простого пропуска заголовка тут недостаточно:
`ИМЯ.RUN` собран из предположения, что будет выполняться по
`0x00002000` - все его собственные `JMP`/`CALL`/`LDA`/`STA` на свои же
метки/переменные это отражают как абсолютные адреса. `LOAD_CHILD`
использует таблицу релокаций из заголовка (см. `BUILD` выше), для
каждого записанного там смещения сдвигает соответствующий 4-байтный
адрес на разницу между адресом уровня и `0x00002000`, и только потом
пишет пропатченные байты в RAM. Если `ИМЯ.RUN` не найден в ТЕКУЩЕЙ
папке - ещё два резервных места, и только потом `STATUS=2`, отказ (в
отличие от `LOAD`/`LOAD_RAW`, которые ищут только в текущей папке):

1. **Там, откуда был загружен ТЕКУЩИЙ выполняющийся top-level процесс**
   (`Disk::lastExecDir` - папочный аналог `lastExecDisk`, обновляется в
   те же два момента - `LOAD`/`LOAD_RAW` в основную песочницу, см.
   `PngLoader`/`MapLoader`/`ModLoader` выше про дисковую половину той
   же идеи). Общая утилита, запускаемая через `exec_child()` (см.
   `C/TOOLS/VIEW.MC`, запускается из `F3` в `C/TOOLS/FM.MC`),
   естественно лежит РЯДОМ с программой, которая её запускает - этот
   резерв находит её там без какой-либо дополнительной настройки:
   собрать один раз в ТОЙ ЖЕ папке, что и исходник вызывающей
   программы, и она найдётся независимо от того, куда к этому моменту
   успел забрести `currentDir` этой программы (у `FM.MC` он постоянно
   меняется вслед за тем, какую папку сейчас показывает панель - почти
   никогда не там, где лежит сама `FM.MC`).
2. КОРЕНЬ диска - последняя попытка, для утилиты, не привязанной к
   одной конкретной вызывающей программе.

RAM - 4 МиБ (`0x00000000`-`0x003FFFFF`, см. `main.cpp`) - адреса
уровней вложенности лежат в отдельной области намного выше
`SHELL_LOAD_ADDRESS` (`0x00020000`), не тесня ни его, ни друг друга: по
256 КиБ на уровень (с большим запасом - самая большая программа в
проекте, `FM.MC`, весит около 20 КБ), 4 уровня занимают 1 МиБ, оставляя
ещё 2+ МиБ RAM полностью свободными. Как и у основной песочницы, размер
не проверяется в рантайме. Эти команды **не вызываются напрямую**
программами - решение, какую из них послать и по какому адресу
вызывать код, целиком на стороне `SHELL.ASM` (`shell_exec_child`, см.
"Мини-C" ниже) - готовый пример использования: `FM.MC`, `Enter` на
файле `*.RUN`.

Имя файла (`NAME`) может быть от 1 до 12 символов - полноценный
формат 8.3 (`ИМЯ.РАСШИРЕНИЕ`, но без принудительной точки, просто до
12 байт). Команды терминала (`type`/`exec`/`create`/`del`/`copy`)
принимают его переменной длины благодаря флагу `CARRY` (см. раздел
"2. Регистры") - раньше, до появления `CARRY`, было вынужденное
ограничение "ровно 7 символов, дополненных пробелами".

## Аргументы командной строки

Как в DOS: пробел после имени программы, а за ним ещё текст - и этот
текст передаётся запущенной программе как аргумент:

    exec view.mc readme.txt
    view readme.txt          ; то же самое, после однократного "build view.mc"

Работает и для `exec ИМЯ`, и для голого автозапуска (`ИМЯ` само по
себе, см. `LOAD_RAW` выше) - `SHELL.ASM` разбивает набранную строку по
ПЕРВОМУ пробелу после имени программы (`find_name_and_arg_len`): всё до
него - имя файла (по-прежнему не длиннее 12 байт - слишком длинное имя
тихо игнорируется целиком, как и нераспознанная команда), всё после
него - аргумент, который передаётся программе через фиксированный
низкоадресный канал:

    0x00010005              CMD_ARGS_LEN   (1 байт - длина аргумента, 0 = нет)
    0x00010006-0x00010015   CMD_ARGS_TEXT  (16 байт - сырой текст аргумента)

Тот же тип фиксированного "интерфейсного" адреса, что и `lastKey`
(`0x00010001`, см. "Прерывания") - зарезервирован по договорённости,
безопасно вдали от роста кода, поскольку `main.cpp`/другие программы не
видят меток ассемблера. В отличие от `lastKey`, его читает не
`main.cpp` - его читает та программа, которую шелл только что запустил.
`SHELL.ASM` ВСЕГДА выставляет его перед `CALL 0x00002000`
(`copy_args_to_fixed`, вызывается из `cmd_exec_run` - общего хвоста и
`cmd_exec`, и `cmd_autorun`), в том числе выставляет длину 0, если
аргумент не был набран - та же логика, что и обнуление `lastKey`:
иначе программа увидела бы СТАРЫЙ аргумент, оставшийся от того, что
запускалось до неё.

Программа, запущенная через `exec_child()` (см. "Запуск дочерней
программы: exec_child()" ниже), получает аргумент тем же способом, но
канал заполняет сама ВЫЗЫВАЮЩАЯ программа, напрямую, перед вызовом
`exec_child()` - `shell_exec_child` его НЕ трогает (тот же прецедент,
что и `EXEC_CHILD_DISK`, `0x0000000F`, который он тоже никогда не
обнуляет). Программе, которой аргументы не нужны, достаточно просто
никогда не читать `CMD_ARGS_LEN` - устаревшее значение от чужого
предыдущего запуска безвредно, если его никто не смотрит.

Из Мини-C оба уже объявлены сами по себе - `CMD_ARGS_LEN`, `cmdArgs[16]`,
`EXEC_CHILD_DISK` - см. "Встроенные константы регистров устройств
(прелюдия)" ниже. Готовый пример: `F3` в `C/TOOLS/FM.MC`
(`view_selected_file()`) запускает `C/TOOLS/VIEW.MC` с именем
выделенного файла в качестве аргумента.


## TextAttr

Плоскость цветовых атрибутов - отдельное устройство, не встроенное в
`Text VRAM` (чтобы не трогать уже занятые адреса `Text VRAM`/
`DebugPort`/дисков). Та же сетка 80x25, что и `Text VRAM`, но байт
означает не символ, а цвет: младший нибл (биты 0-3) - цвет символа
(0-15), старший нибл (биты 4-7) - цвет фона (0-15). Палитра -
стандартная 16-цветная ANSI: `0`-`7` обычные цвета (чёрный, красный,
зелёный, жёлтый, синий, пурпурный, голубой, белый), `8`-`15` - яркие
версии тех же цветов.

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 0-1999 | сетка 80x25 | один байт цвета на ту же ячейку, что в `Text VRAM` |
| 2000 | SCROLL | сдвигает цвета на одну строку вверх, как у `Text VRAM` |
| 2001 | CLEAR | сбрасывает всю сетку в цвет по умолчанию (`0x07`) |

Адреса: `0xF000080C` (первая ячейка) - `0xF0000FDB` (последняя
ячейка), `SCROLL` = `0xF0000FDC`, `CLEAR` = `0xF0000FDD`.

Индексация identична `Text VRAM` (`index = y * 80 + x`) - ячейка
`(x, y)` в обоих устройствах лежит по одному и тому же относительному
смещению, только базовые адреса разные. **Важно**: при прокрутке или
очистке `Text VRAM` нужно применить `SCROLL`/`CLEAR` и к `TextAttr`
тоже - иначе цвет "отстаёт" от текста (так и сделано в `advance_row`/
`cmd_cls`/`cmd_reset` в `boot.asm`).

Дефолтный цвет всей сетки при старте - `0x07` (светло-серый на
чёрном, классика DOS).

**Прозрачный фон (только в видеоконсоли, см. "VideoConsole" ниже)**:
значение старшего нибла `8` (`TRANSPARENT_BG`) означает не тёмно-серый
фон, а "фон не рисовать вообще" - виден слой `VideoCard`/то, что уже
было на экране под этой ячейкой, рисуется только сам символ нужным
цветом. Ни одна программа/утилита в этом проекте не использует
значения фона `8-15` как настоящий цвет (везде фон `0`/`1`/`7`), так
что значение `8` было безопасно занято под этот спецсмысл - как ЦВЕТ
СИМВОЛА (младший нибл) `8` по-прежнему работает как обычный
тёмно-серый, особый смысл только у старшего нибла. В резервном
текстовом режиме (`console=text`) это правило не действует - там нет
слоя `VideoCard`, под которым что-то прятать, фон `8` рисуется как
обычный тёмно-серый ANSI-цвет. Пример - `C/DEMOS/SNOW3D.MC`
(`place_snowflake()`): `set_color(col, row, fg, BG_TRANSPARENT)`
рисует "снежинку" без чёрного прямоугольника вокруг неё поверх
графики.

Пример: покрасить всю строку `row` в ярко-голубой на чёрном
(`0x0E`) - подпрограмма `goto_attr_row_start` в `boot.asm`
(аналог `goto_row_start`, но с базой `TextAttr`) считает нужный
адрес, дальше просто `STX`/`INCHL` 80 раз (готовая подпрограмма
`print_char_n`):

    LDI A, <row>
    STA row
    CALL goto_attr_row_start   ; HL = 0xF000080C + row*80
    LDI A, 80
    STA tmp2
    LDI A, 0x0E                ; цвет
    CALL print_char_n

Готовый пример использования - рамка вокруг баннера в `draw_banner`
(`boot.asm`).

## VideoConsole

Единственное графическое окно на весь процесс (Win32 + OpenGL/WGL,
собственный поток, не блокирует цикл CPU - тот же принцип, что у
`VideoCard` ниже). Не устройство шины - нет регистров/MMIO, программы
работают точно так же, как если бы никакой видеоконсоли не было
(пишут в `Text VRAM`/`TextAttr`/`VideoCard` как обычно). Включается по
умолчанию (`console=video` в `config.txt`); в резервном текстовом
режиме (`console=text`) вместо неё - обычное окно консоли Windows с
ANSI-выводом, см. "Устройства - сводка" в начале документа.

Два слоя одной картинки, а не два окна:

- **Текст** - сетка 80x25, каждая ячейка рисуется зашитым в код
  битмап-шрифтом CP866 8x16 (никаких файлов шрифта на диске). Размер
  окна = 640x400 умножить на масштаб (`video_scale` в `config.txt`,
  по умолчанию 2 → окно 1280x800) - целочисленный, глиф остаётся
  резким без сглаживания.
- **Графика `VideoCard`** - фон: если `VideoCard` активна (между
  `MODE_ON`/`MODE_OFF`, см. её раздел ниже), её кадр 320x240 (4:3)
  вписывается в канву 640x400 (8:5) методом "ближайший сосед" с
  сохранением пропорций и центрированием - чёрные поля по бокам
  (~53px на базовом масштабе), т.к. пропорции разные. Нативное
  разрешение `VideoCard`/`Gpu3D` при этом не меняется - оно зашито и в
  проекцию 3D, и в уже существующие демки/игры.

Правила прозрачности текстового слоя (см. также "ConsoleLayer" и
"TRANSPARENT_BG" в разделе "TextAttr" выше) - под текстом, где он
прозрачен, виден слой `VideoCard`/то, что уже было нарисовано:

- ячейка `(пробел, атрибут 0x07 по умолчанию)` - "нетронутая" после
  `CLEAR`/загрузки - не рисуется вообще, целиком прозрачна;
- ячейка с фоном `TRANSPARENT_BG` (`8`, см. "TextAttr" выше) -
  рисуется только сам символ нужным цветом, фон не трогается - это и
  есть механизм HUD/эффектов поверх графики (пример - "снежинки" в
  `C/DEMOS/SNOW3D.MC`, см. раздел "ConsoleLayer" ниже).

Ввод клавиатуры - то же самое окно ловит и `WM_CHAR` (обычные символы,
Enter/Backspace/Tab/Esc/Ctrl+буква), и `WM_KEYDOWN`/`WM_SYSKEYDOWN`
(стрелки/Home/End/PgUp/PgDn/Delete/F1-F10/Alt+F1/Alt+F2) - вторые
`WM_CHAR` не порождает вовсе, так что без отдельной обработки они бы
не доходили до программы. Клавиши преобразуются в те же самые
DOS-скан-коды, что и настоящая консоль отдаёт через `_getch()`
(`KEYBOARD_DATA`), включая двухбайтовую последовательность
(ведущий байт `0` для F-клавиш/`0xE0` для остальных, затем сам код) -
программе, читающей `KEYBOARD_DATA`, без разницы, откуда на самом деле
пришла клавиша.

## ConsoleLayer

Один переключаемый бит - виден ли текстовый слой видеоконсоли поверх
графики `VideoCard`. Запись `0` - скрыть, любое другое значение -
показать; чтение - текущее состояние (0/1). По умолчанию (после
старта ВМ) - видимый.

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 0 | CONSOLE_VISIBLE (чтение/запись) | 0 = скрыт, 1 (или любое ненулевое) = виден |

Адрес: `0xF0001042` (см. "Встроенные константы регистров устройств
(прелюдия)" в разделе "Мини-C" - там же готовая константа
`CONSOLE_VISIBLE`).

Два независимых источника записи:

- **`VideoCard`** (см. её раздел ниже) - `MODE_ON` автоматически
  прячет консоль (но только на переходе выкл→вкл - повторный `MODE_ON`
  во время уже идущей сессии не сбрасывает то, что программа включила
  сама), `MODE_OFF` всегда возвращает её обратно, чтобы графическая
  программа не оставляла экран без консоли после выхода.
- **Сама программа** - "комбинированный режим": включить консоль
  обратно, пока графика уже активна, и печатать текст (`print_char`/
  `set_color`/`clear_screen`/`poke()` и так пишут в `Text VRAM`/
  `TextAttr` в любой момент, вне зависимости от того, показывается ли
  сейчас накопленное - `CONSOLE_VISIBLE` решает только это).

Пример - `C/DEMOS/SNOW3D.MC`: `MODE_ON` прячет консоль автоматически,
демка тут же включает её обратно (`poke(CONSOLE_VISIBLE, 1)`) и
продолжает печатать разноцветные "снежинки" (с `TRANSPARENT_BG`, см.
"TextAttr" выше) поверх тайловой карты/спрайта/вращающегося 3D-куба -
живой пример текста и графики одновременно в одном окне.

## VideoCard

Растровый видеорежим 320x240, RGB (3 байта на пиксель). В отличие от
`Text VRAM`/`TextAttr`, framebuffer НЕ адресуется побайтово через шину
(320*240*3 = 230400 байт - писать их по одному через CPU было бы
непрактично медленно). Вместо этого - компактный командный протокол
(регистры + `COMMAND`-триггер), как у `Disk`: framebuffer целиком живёт
внутри устройства на C++ стороне.

Своего окна/потока/OpenGL-контекста у устройства НЕТ - единственный
экран на весь процесс держит `VideoConsole` (см. её раздел выше),
`VideoCard` лишь ещё один слой в его композиции: `MODE_ON`/`MODE_OFF`
только выставляют флаг "активна" (и заодно переключают `ConsoleLayer`,
см. её раздел выше) - `VideoConsole` сам вписывает готовый кадр
320x240 в свою канву на каждой перерисовке, если флаг взведён.
Тяжёлая работа композиции тем не менее НЕ делается внутри `tick()`
устройства (`VideoCard` вообще не переопределяет `tick()`) -
`tick()` вызывается на КАЖДОЕ обращение к шине (см.
`CPU::busRead`/`busWrite`), и делать там что-то дорогое повторило бы
старый баг с `Keyboard` (см. "Keyboard" выше), только гораздо
серьёзнее. В резервном текстовом режиме (`console=text`) своего
экрана у `VideoCard` нет вообще - графика в нём недоступна.

Координаты 0-319/0-239 не влезают в один байт (максимум 255) -
передаются как LOW+HIGH байт (16 бит), как `Disk` делает для
`fileSize`.

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 0 | X_LOW | X, младший байт |
| 1 | X_HIGH | X, старший байт |
| 2 | Y_LOW | Y, младший байт |
| 3 | Y_HIGH | Y, старший байт |
| 4 | W_LOW | ширина (для FILL_RECT), младший байт |
| 5 | W_HIGH | ширина, старший байт |
| 6 | H_LOW | высота (для FILL_RECT), младший байт |
| 7 | H_HIGH | высота, старший байт |
| 8 | R | компонент цвета, 0-255 |
| 9 | G | компонент цвета, 0-255 |
| 10 | B | компонент цвета, 0-255 |
| 11 | COMMAND (запись = триггер) | 1=MODE_ON, 2=MODE_OFF, 3=CLEAR, 4=SET_PIXEL, 5=FILL_RECT |
| 12 | STATUS (только чтение) | 0=ok, 1=координата/размер вне экрана (0-319/0-239) |

Адреса: `0xF0000FDE` (X_LOW) - `0xF0000FEA` (STATUS) - регистры фона;
следом сразу продолжается блок регистров спрайтов (см. "Аппаратные
спрайты" ниже).

Команды (`COMMAND`):

- **1 (MODE_ON)** - выставляет флаг "активна" - `VideoConsole` начинает
  вписывать кадр 320x240 в свою канву на каждой перерисовке (см. её
  раздел выше). Автоматически прячет текстовый слой консоли через
  `ConsoleLayer` (только на переходе выкл→вкл - см. "ConsoleLayer"
  выше). Не блокирует вызывающую программу.
- **2 (MODE_OFF)** - снимает флаг "активна" и возвращает текстовый
  слой консоли обратно (`ConsoleLayer`, безусловно). Framebuffer в
  памяти не сбрасывается. Явный `MODE_OFF` перед выходом программы
  рекомендуется, чтобы консоль не осталась спрятанной.
- **3 (CLEAR)** - заливает весь framebuffer цветом `R,G,B` (игнорирует
  X/Y/W/H).
- **4 (SET_PIXEL)** - красит один пиксель `(X, Y)` в цвет `R,G,B`.
- **5 (FILL_RECT)** - заливает прямоугольник `X,Y,W,H` цветом `R,G,B`
  одним вызовом (без цикла на стороне ассемблера) - этим стоит
  пользоваться вместо `SET_PIXEL` в цикле для больших областей
  (быстрее и на порядок меньше кода).

Пример - залить весь экран синим:

    LDI A, 0
    STA 0xF0000FE6      ; R = 0
    STA 0xF0000FE7      ; G = 0
    LDI A, 255
    STA 0xF0000FE8      ; B = 255
    LDI A, 3
    STA 0xF0000FE9      ; COMMAND = CLEAR

Полный рабочий пример с движением, отражением от краёв и сменой
цвета - `C/DEMOS/DEMO.ASM` (запускается из шелла: `cd demos`, затем
`exec demo.asm` - см. "Disk" про `cd` и ModLoader/PngLoader/MapLoader
про то, почему ресурсы демок резолвятся из ТЕКУЩЕЙ папки).
Там же показан приём перевода 8-битной "юнитной" координаты в
настоящий 16-битный пиксель через `ADD A, A` (`A = A*2`, `CARRY` =
старший бит результата) - см. `ADD`/`ADC` выше про этот приём.

### Аппаратные спрайты

16 независимых битмапов 32x32 (RGB), каждый со своей позицией и
видимостью - видеокарта сама накладывает их поверх фона при рендере
(в рендер-потоке, см. выше), без перерисовки фона под ними и без
ручного стирания старой позиции из ассемблера, в отличие от
`SET_PIXEL`/`FILL_RECT`.

Прозрачность - через цвет-ключ (chroma key): пиксель спрайта цвета
`(255, 0, 255)` (маджентовый) считается прозрачным и не рисуется при
композиции. Из этого следует единственное ограничение - нарисовать
внутри спрайта непрозрачный пиксель именно такого цвета нельзя.

Регистры продолжают адресный блок `VideoCard` (смещения 13-25, сразу
после `STATUS`):

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 13 | SPRITE_INDEX | какой спрайт (0-15) выбран для регистров ниже |
| 14 | SPRITE_PIXEL_LOW | индекс пикселя внутри спрайта (0-1023), младший байт |
| 15 | SPRITE_PIXEL_HIGH | индекс пикселя, старший байт |
| 16 | SPRITE_X_LOW | X спрайта на экране, младший байт |
| 17 | SPRITE_X_HIGH | X, старший байт |
| 18 | SPRITE_Y_LOW | Y спрайта на экране, младший байт |
| 19 | SPRITE_Y_HIGH | Y, старший байт |
| 20 | SPRITE_VISIBLE | 0/1 - показывать ли спрайт |
| 21 | SPRITE_R | компонент цвета для записи пикселя спрайта |
| 22 | SPRITE_G | компонент цвета |
| 23 | SPRITE_B | компонент цвета |
| 24 | SPRITE_COMMAND (запись = триггер) | 1=WRITE_PIXEL, 2=CLEAR |
| 25 | SPRITE_STATUS (только чтение) | 0=ok, 1=индекс спрайта/пикселя вне диапазона |

`SPRITE_X_LOW/HIGH`, `SPRITE_Y_LOW/HIGH` и `SPRITE_VISIBLE` действуют
сразу по записи, без команды - двигать спрайт каждый кадр должно быть
дёшево (несколько `STA`, без лишнего байта-команды).

Команды (`SPRITE_COMMAND`):

- **1 (WRITE_PIXEL)** - пишет `SPRITE_R/G/B` в пиксель
  `SPRITE_PIXEL` битмапа спрайта `SPRITE_INDEX`, затем
  автоинкрементирует `SPRITE_PIXEL` по модулю 1024 - позволяет
  залить весь битмап подряд простым циклом (`STA R; STA G; STA B;
  STA COMMAND`, 1024 раза), без ручного пересчёта индекса.
- **2 (CLEAR)** - заливает весь битмап выбранного спрайта цветом-ключом
  (255,0,255), т.е. делает его полностью прозрачным/пустым.

Пример - определить спрайт 0 как сплошной красный квадрат 32x32 и
показать его в точке (50, 50):

    LDI A, 0
    STA 0xF0000FEB      ; SPRITE_INDEX = 0

    LDI A, 255
    STA 0xF0000FF3      ; SPRITE_R = 255
    LDI A, 0
    STA 0xF0000FF4      ; SPRITE_G = 0
    STA 0xF0000FF5      ; SPRITE_B = 0
                          ; (заполнить все 1024 пикселя - см. ниже)

sprite_fill_loop:
    LDI A, 1
    STA 0xF0000FF6      ; SPRITE_COMMAND = WRITE_PIXEL (авто-инкремент)
    ; ... повторить 1024 раза (цикл с проверкой SPRITE_PIXEL_LOW/HIGH) ...

    LDI A, 50
    STA 0xF0000FEE      ; SPRITE_X_LOW = 50
    LDI A, 0
    STA 0xF0000FEF      ; SPRITE_X_HIGH = 0
    LDI A, 50
    STA 0xF0000FF0      ; SPRITE_Y_LOW = 50
    LDI A, 0
    STA 0xF0000FF1      ; SPRITE_Y_HIGH = 0
    LDI A, 1
    STA 0xF0000FF2      ; SPRITE_VISIBLE = 1

Адреса: `0xF0000FDE` (X_LOW) - `0xF0000FF7` (SPRITE_STATUS) - фон и
спрайты; следом сразу продолжается блок скролла тайловой карты (см.
"Аппаратные тайлы и скролл" ниже).

### Аппаратные тайлы и скролл

Второй слой поверх фона (но ПОД 3D-слоем и спрайтами) - тайловая
карта: набор повторяющихся плиток 32x32 (тайлсет, до 128 разных
тайлов) и большая карта индексов тайлов (может быть шире/выше экрана
320x240), которая скроллится под неподвижным на экране спрайтом
персонажа. Полный порядок отрисовки слоёв в рендер-потоке: фон
(`framebuffer`) -> тайлы (если карта загружена) -> 3D-слой (если
активен, см. `Gpu3D` ниже) -> спрайты - тайлы полностью перекрывают
фон в видимой области, 3D-слой перекрывает тайлы там, где реально
что-то нарисовал, спрайты рисуются поверх абсолютно всего (это и есть
слой UI - HUD/иконки поверх 3D-сцены).

Сам тайлсет заполняется через `PngLoader` (`EXTRACT_TILE`, см. ниже),
сама карта - через `MapLoader` (текстовый файл, см. ниже). У
`VideoCard` из тайловой части - только два 16-битных регистра
скролла, продолжающие адресный блок сразу после спрайтов:

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 26 | SCROLL_X_LOW | скролл карты по X, младший байт |
| 27 | SCROLL_X_HIGH | старший байт |
| 28 | SCROLL_Y_LOW | скролл по Y, младший байт |
| 29 | SCROLL_Y_HIGH | старший байт |

Действуют сразу по записи (без команды, как позиция спрайта) и
автоматически ограничиваются границами карты (`0` - `mapWidth*32-320`
по X, аналогично по Y) - "убежать" скроллом за край карты нельзя, само
устройство подрежет значение. Пока карта не загружена (`MapLoader` ещё
ни разу не отработал), тайловый слой не рисуется вообще - старые
демки без тайлов (`DEMO.ASM`, `SPRITES.ASM`) не видят разницы.

Адрес: `0xF0000FF8` (SCROLL_X_LOW) - `0xF0000FFB` (SCROLL_Y_HIGH).

Полный рабочий пример - `C/DEMOS/TILEDEMO.ASM` (`cd demos`, затем
`exec tiledemo.asm`): персонаж неподвижен в центре экрана, карта под
ним скроллит со сменой направления по таймеру.

## PngLoader

Грузит PNG-файл из ТЕКУЩЕЙ папки ТОГО диска (C или D), с которого
командой `exec` была реально запущена выполняющаяся сейчас программа
(`Disk::lastExecDisk` - см. "Disk" ниже про этот статический
указатель, общий для обоих экземпляров `Disk`; до первого `exec` за
всё время работы VM по умолчанию используется диск C). Та же папка,
что меняет команда `cd`, и которую уже использует `exec`/`type`/`dir`
- поэтому запущенная из `C:\DEMOS` (или скопированная на `D:\DEMOS`)
программа (см. `C/DEMOS/*.ASM`) находит свои же ресурсы рядом с собой,
на том же диске, откуда её запустили, без специального механизма
"программа знает свой путь". И вырезает из него квадраты 32x32 прямо в
видеопамять `VideoCard` - в спрайт ИЛИ в тайл тайлсета. PNG - сжатый
формат (zlib/deflate) - декодировать его в ассемблере этого CPU
нереально, поэтому весь разбор формата (через `stb_image.h`) целиком
спрятан на стороне C++: ассемблеру видны только команды "загрузи
файл", "вырежи регион в спрайт N" и "вырежи регион в тайл N".

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 0-11 | NAME0-11 | имя PNG-файла (как у `Disk`) |
| 12 | SRC_X_LOW | X верхнего левого угла вырезаемого региона, младший байт |
| 13 | SRC_X_HIGH | старший байт |
| 14 | SRC_Y_LOW | Y региона, младший байт |
| 15 | SRC_Y_HIGH | старший байт |
| 16 | SPRITE_INDEX | номер спрайта-приёмника у `VideoCard` (0-15, для EXTRACT) |
| 17 | COMMAND (запись = триггер) | 1=LOAD, 2=EXTRACT, 3=EXTRACT_TILE |
| 18 | STATUS (только чтение) | 0=ok, 1=файл не найден/не декодировался, 2=регион вне картинки, 3=неверный SPRITE_INDEX/TILE_INDEX |
| 19 | TILE_INDEX | номер тайла-приёмника у `VideoCard` (0-127, для EXTRACT_TILE) |

Адреса: `0xF0000FFE` (NAME0) - `0xF0001011` (TILE_INDEX).

Команды:

- **1 (LOAD)** - декодирует файл `NAME` в RGBA и кэширует результат
  внутри устройства (ширина/высота/пиксели) до следующего `LOAD` -
  один `LOAD` спрайтшита/тайлсета обслуживает много последующих
  `EXTRACT`/`EXTRACT_TILE` без повторного декодирования.
- **2 (EXTRACT)** - вырезает квадрат 32x32 из закэшированной картинки
  начиная с `(SRC_X, SRC_Y)`, конвертирует прозрачность (альфа < 128 -
  пиксель становится цветом-ключом `(255,0,255)` у `VideoCard`, иначе
  копируется RGB как есть - модель спрайтов и тайлов не хранит альфу,
  только chroma-key, см. "Аппаратные спрайты" выше) и пишет результат
  в спрайт `SPRITE_INDEX`.
- **3 (EXTRACT_TILE)** - то же самое, но пишет в тайл `TILE_INDEX`
  тайлсета `VideoCard` (см. "Аппаратные тайлы и скролл" выше) вместо
  спрайта.

Пример - загрузить спрайтшит и положить ячейку `(64, 0)` в спрайт 2:

    LDI A, 83   ; 'S'
    STA 0xF0000FFE
    LDI A, 80   ; 'P'
    STA 0xF0000FFF
    ; ... остальные буквы имени файла в NAME2-11, лишние - в 0 ...

    LDI A, 1
    STA 0xF000100F      ; COMMAND = LOAD

    LDA 0xF0001010       ; STATUS - проверить перед EXTRACT
    LDI B, 0
    CMP B
    JNZ png_error

    LDI A, 64
    STA 0xF000100A      ; SRC_X_LOW = 64
    LDI A, 0
    STA 0xF000100B      ; SRC_X_HIGH = 0
    STA 0xF000100C      ; SRC_Y_LOW = 0
    STA 0xF000100D      ; SRC_Y_HIGH = 0
    LDI A, 2
    STA 0xF000100E      ; SPRITE_INDEX = 2
    LDI A, 2
    STA 0xF000100F      ; COMMAND = EXTRACT

Полный рабочий пример - `C/DEMOS/SPRITES.ASM` (`cd demos`, затем
`exec sprites.asm`): грузит спрайтшит, расставляет несколько
персонажей неподвижным фоном и один двигает по экрану как в
`C/DEMOS/DEMO.ASM`, только через `SPRITE_X/Y`, а не `FILL_RECT`.

## MapLoader

Грузит текстовый файл тайловой карты из ТЕКУЩЕЙ папки того диска, с
которого был запущен `exec`нутый файл (см. `PngLoader` выше про
`Disk::lastExecDisk`), и кладёт его прямо в `VideoCard` (см. "Аппаратные тайлы и скролл" выше) - какой
тайл стоит в какой клетке карты. Разбор текста - на стороне C++, тем же
рассуждением, что и разбор PNG у `PngLoader`: городить парсер текста в
ассемблере этого CPU ради, по сути, разового действия при старте
программы не имеет смысла.

Формат файла - обычный текст: каждая строка файла - одна строка
карты, десятичные индексы тайлов (0-127) через пробел, все строки
одинаковой длины (карта - прямоугольник). Пустые строки в конце файла
игнорируются. Пример фрагмента карты 8x3:

    0 0 0 1 1 1 0 0
    0 2 2 2 2 2 0 0
    0 2 3 3 3 2 0 0

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 0-11 | NAME0-11 | имя текстового файла карты (как у `Disk`) |
| 12 | COMMAND (запись = триггер) | 1 = LOAD |
| 13 | STATUS (только чтение) | 0=ok, 1=файл не найден, 2=ошибка разбора (не прямоугольная карта, пустой файл, индекс тайла вне 0-127) |

Адреса: `0xF0001012` (NAME0) - `0xF000101F` (STATUS).

Команда **1 (LOAD)** читает файл `NAME`, разбирает его по формату
выше и одним вызовом заменяет текущую карту `VideoCard` целиком (новая
карта заменяет старую вместе с размерами; скролл при этом сбрасывается
в `(0, 0)`, чтобы не остаться за пределами новой, возможно меньшей,
карты).

Пример - загрузить `MAP.TXT`:

    LDI A, 77   ; 'M'
    STA 0xF0001012
    LDI A, 65   ; 'A'
    STA 0xF0001013
    LDI A, 80   ; 'P'
    STA 0xF0001014
    LDI A, 46   ; '.'
    STA 0xF0001015
    LDI A, 84   ; 'T'
    STA 0xF0001016
    LDI A, 88   ; 'X'
    STA 0xF0001017
    LDI A, 84   ; 'T'
    STA 0xF0001018
    LDI A, 0
    STA 0xF0001019      ; и так далее NAME7-11 = 0

    LDI A, 1
    STA 0xF000101E      ; COMMAND = LOAD

    LDA 0xF000101F       ; STATUS
    LDI B, 0
    CMP B
    JNZ map_error

Полный рабочий пример - `C/DEMOS/TILEDEMO.ASM` (`cd demos`, затем
`exec tiledemo.asm`), карта - `C/DEMOS/MAP.TXT`.

## SoundCard

Проигрывает уже разобранную трекерную песню (см. `ModLoader` ниже -
разбор формата .mod целиком там, `SoundCard` только воспроизводит
готовую структуру: сэмплы + паттерны + order-таблица). Секвенсор,
микшер и вывод звука (`winmm`/`waveOut*`) целиком живут в отдельном
`std::thread`, независимом от цикла CPU - та же причина, что и у
`VideoCard`: `tick()` устройства вызывается на КАЖДОЕ обращение к шине
(см. `CPU::busRead`/`busWrite`) - тяжёлая работа там повторила бы
старый баг с `Keyboard`, только гораздо серьёзнее. `SoundCard` вообще
не переопределяет `tick()`.

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 0 | COMMAND (запись = триггер) | 1=PLAY, 2=STOP, 3=PAUSE, 4=RESUME |
| 1 | STATUS (только чтение) | 0=стоп/готово, 1=играет, 2=на паузе, 3=песня не загружена |
| 2 | VOLUME | общая громкость 0-255 (по умолчанию 255), действует сразу по записи |
| 3-6 | CHANNEL0-3_VOLUME (только чтение) | текущая громкость канала, 0-64 (нативные единицы ProTracker, та же шкала, что у `Cxx`) |
| 7 | ROW (только чтение) | текущая строка паттерна, 0-63 |
| 8 | ORDER_POS (только чтение) | текущая позиция в order-таблице, 0-127 |
| 9 | PATTERN_ROW_SELECT (запись) | строка ТЕКУЩЕГО играющего паттерна для запроса, 0-63 |
| 10 | PATTERN_CHANNEL_SELECT (запись) | канал для запроса, 0-3 |
| 11 | PATTERN_NOTE (только чтение) | индекс ноты в ячейке (row,channel), 0-35, `255`=нет ноты |
| 12 | PATTERN_SAMPLE (только чтение) | номер сэмпла в ячейке, 0-31 (`0`=нет) |
| 13 | PATTERN_EFFECT (только чтение) | номер эффекта в ячейке, 0-15 |
| 14 | PATTERN_PARAM (только чтение) | параметр эффекта в ячейке, 0-255 |

Адреса: `0xF0001066` (COMMAND) - `0xF0001074` (PATTERN_PARAM). Про дыру на
старом месте, `0xF0001042`-`0xF0001044`: раньше блок стоял именно там,
прямо перед `Gpu3D`, но стал тесен, когда добавились регистры
визуализации ниже, а расширить его на месте значило бы сдвинуть
`Gpu3D` и переписать каждый жёстко зашитый адрес в `CUBE3D.ASM`.
Перенос всего блока в свободное место сразу после `Gpu3D` избавил от
этого целиком - адреса на этой шине никогда не обязаны идти подряд без
пропусков. Из этой дыры `0xF0001042` с тех пор занят под `ConsoleLayer`,
а `0xF0001043` - под `ModLoaderDiskSelect` (см. "ModLoader", DISK_SELECT)
- свободным всё ещё остаётся только `0xF0001044`.

### Регистры визуализации (CHANNEL\*\_VOLUME/ROW/ORDER_POS)

Эти три read-only регистра зеркалят состояние секвенсора, которое уже
существовало внутри (текущая громкость каждого канала, текущая
строка, позиция в order-таблице), но раньше не было видно на шине -
добавлены специально, чтобы программа могла рисовать живой визуализатор
(см. `C/DEMOS/MUSIC2.MC`), не трогая логику самого секвенсора. Как и
`VOLUME`, они реализованы через `std::atomic<uint8_t>`, обновляемые раз
за тик из аудио-потока - CPU-поток читает их без какой-либо блокировки,
по той же причине, что и `VOLUME` выше. Все три читаются как `0` до
загрузки песни или пока воспроизведение остановлено.

`CHANNEL0-3_VOLUME` проще всего читать из Мини-C: это 4 байта подряд,
поэтому маппированный массив (`int channelVol[4] = 0xF0001069;`) даёт
рантайм-индексацию по всем четырём каналам одной переменной - тот же
приём, что `SNAKE.MC` использует для игрового поля. `ROW`/`ORDER_POS` -
отдельные байты по фиксированным адресам, для них достаточно обычного
`peek()`.

### Регистры запроса ячейки паттерна (PATTERN_*)

В отличие от `CHANNEL*_VOLUME`/`ROW`/`ORDER_POS` выше, эти шесть
регистров - НЕ зеркала, обновляемые раз за тик аудио-потоком, а
вычисляются заново при каждом чтении: запись `PATTERN_ROW_SELECT`
(0-63) и `PATTERN_CHANNEL_SELECT` (0-3) выбирает ячейку в ТЕКУЩЕМ
играющем паттерне (`song.orderTable[ORDER_POS]`), дальше `PATTERN_NOTE`/
`PATTERN_SAMPLE`/`PATTERN_EFFECT`/`PATTERN_PARAM` читают её поля.
`PATTERN_NOTE` - не сырой period, а готовый индекс 0-35 в той же
36-нотной таблице, что и `PERIOD_TABLE` (см. ниже) - подбирается точным
совпадением с period ячейки, `255` - если ячейка без ноты (period=0)
или period не совпал ни с одним стандартным значением (необычный
finetune и т.п.). Любой некорректный запрос (песня не загружена,
`ORDER_POS`/номер паттерна вне диапазона, `PATTERN_ROW_SELECT >= 64`
или `PATTERN_CHANNEL_SELECT >= 4`) даёт "пустую" ячейку (`NOTE=255`,
остальное `0`), а не ошибку - тот же стиль, что и у read-регистров всей
этой шины.

Добавлены ради живого просмотра нот/сэмплов/эффектов - "едущих блоков"
`C/TOOLS/PLAYER.MC`, "в духе" классических трекеров (см. "Плейлист
(PLAY.LST)" ниже, где этот же файл целиком описан, - подраздел
"Едущие блоки"). Запрос дотягивается только до ТЕКУЩЕГО играющего
паттерна - строка, уехавшая за его начало/конец (0-63), не подтягивает
соседний паттерн по order-таблице; вызывающая программа сама решает,
что показывать в этом случае (пустую строку и т.п.).

`getQueryCell()` (`SoundCard.cpp`) блокирует `songMutex` на время
чтения - `song` (сэмплы/паттерны/order-таблица) целиком заменяется
`loadSong()` при каждой новой `LOAD` через `ModLoader`, и это тот же
объект, из которого читает `getQueryCell()`.

Команды:

- **1 (PLAY)** - запускает воспроизведение с начала песни (если уже
  играет - не перезапускает; если на паузе - снимает паузу). Ничего
  не делает и оставляет `STATUS=3`, если песня ещё не загружена через
  `ModLoader`.
- **2 (STOP)** - останавливает воспроизведение и закрывает
  аудио-поток. Следующий `PLAY` начнёт песню заново с начала (не с
  места остановки - для этого есть `PAUSE`/`RESUME`).
- **3 (PAUSE)** / **4 (RESUME)** - приостановить/возобновить без
  сброса позиции в песне (тишина вместо аудио, секвенсор не крутится,
  пока на паузе).

Если на компьютере нет звукового устройства (или недоступно) -
`waveOutOpen` внутри `PLAY` тихо завершается неудачей: воспроизведения
не будет, но процесс не падает и не бросает исключений.

### Секвенсор и эффекты

Тик-ориентированный секвенсор, как в оригинальном ProTracker:
`speed` (тиков на строку, по умолчанию 6) и `tempo` (BPM, по
умолчанию 125) определяют длительность тика (`2500 / tempo` мс),
строка длится `speed` тиков. На новой строке - триггер новой ноты
(сэмпл + частота из period, `freq = 8363 * 428 / period`, без учёта
finetune - согласованное упрощение) и громкости; на каждом тике -
эффекты, которые "едут":

| Эффект | Название | Реализовано |
|---|---|---|
| `0xy` | Арпеджио | да - циклит высоту между базовой нотой и +x/+y полутонами каждый тик |
| `1xx` | Portamento up | да - period уменьшается на `xx*4` за тик (с запоминанием последнего ненулевого `xx`) |
| `2xx` | Portamento down | да - симметрично `1xx` |
| `3xx` | Tone portamento | да - едет к period последней указанной ноты, не перезапускает сэмпл |
| `Axy` | Volume slide | да - `x`>0 повышает громкость на `x`/тик, иначе понижает на `y`/тик |
| `Cxx` | Set volume | да |
| `Bxx` | Position jump | да |
| `Dxx` | Pattern break | да (`xx` - BCD-строка перехода в следующем паттерне) |
| `Fxx` | Set speed/tempo | да (`xx<32` - speed, `xx>=32` - tempo) |
| `4xy`,`7xy`,`9xx`,`Exy` и т.д. | Вибрато, тремоло, sample offset, retrigger и другие | нет - нота триггерится как обычно, сам эффект молча игнорируется |

Панорама - классическая амижная раскладка: каналы 0 и 3 - налево,
1 и 2 - направо. Зацикливание - по достижении конца order-таблицы
(длина - байт 950 файла) секвенсор переходит на `restart position`
(байт 951) - песня играет бесконечно, как и положено трекерной музыке,
пока не придёт `STOP`.

Пример - запустить уже загруженную песню и остановить по Ctrl+Q (полный
рабочий пример - `C/DEMOS/MUSIC.ASM`, `cd demos` + `exec music.asm`):

    LDI A, 1
    STA 0xF0001066      ; SoundCard COMMAND = PLAY
    ...
    LDI A, 2
    STA 0xF0001066      ; SoundCard COMMAND = STOP

## ModLoader

Читает и разбирает трекерный `.mod`-файл из ТЕКУЩЕЙ папки того диска,
с которого был запущен `exec`нутый файл (см. `PngLoader` выше про
`Disk::lastExecDisk`), на стороне C++ и кладёт готовую песню в
`SoundCard` одним вызовом. MOD - бинарный
формат с собственным секвенсором
(сэмплы, паттерны, order-таблица, эффекты) - разобрать его в
ассемблере этого CPU так же нереально, как декодировать PNG (см.
`PngLoader`) - ассемблеру видна только команда "загрузи файл".

Поддерживается стандартный ProTracker MOD - 31 сэмпл, 4 канала,
сигнатура `M.K.`/`M!K!`/`FLT4`/`4CHN` (все четыре означают одно и то
же: 4-канальный 31-сэмпловый формат). Другие сигнатуры (больше/меньше
каналов, старые 15-сэмпловые Soundtracker-модули и т.д.) дают
`STATUS=2`, не крашат.

Имя файла - **32 байта**, не 12, как у `Disk`/`PngLoader`/`MapLoader`:
сам формат `.mod` никак не привязан к 8.3-конвенции, которой следуют
остальные загрузчики - имя длиннее 12 байт `ModLoader` разберёт без
проблем. `ModLoader` не идёт через `Disk` (читает файл сам), так что
ограничение 12 байт у остальных - это только их собственный выбор, а
не общее правило шины. Конкретный `.mod` в этом репозитории,
`C/DEMOS/SPACE_~1.MOD`, тем не менее назван в DOS-стиле 8.3 с `~1` -
как обрезался бы длинный `space_debris.mod` в настоящем DOS - потому
что то же самое имя ещё и лежит на диске "C" (см. `Disk`) и должно
помещаться в 12-байтный `NAME` там, иначе `FM.MC`/`SHELL.ASM` не
смогли бы его нормально листать/копировать/переименовывать.

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 0-31 | NAME0-31 | имя .mod-файла (см. DISK_SELECT ниже - на каком диске искать) |
| 32 | COMMAND (запись = триггер) | 1 = LOAD |
| 33 | STATUS (только чтение) | 0=ok, 1=файл не найден, 2=неподдерживаемый формат (не M.K./4 канала/31 сэмпл), 3=повреждённый/слишком короткий файл |

Адреса: `0xF0001020` (NAME0) - `0xF0001041` (STATUS).

### DISK_SELECT - явный выбор диска (`0xF0001043`)

Отдельное однобайтовое устройство `ModLoaderDiskSelect` (не часть
смежного диапазона `ModLoader` выше - см. врезку "Про дыру на старом
месте" ниже про то, почему оно физически отдельное): `0`=резолвить как
раньше, через `Disk::lastExecDisk` (диск, с которого реально запущена
текущая программа - значение по умолчанию, ничего не меняется для кода,
который никогда не пишет в этот регистр), `1`=принудительно диск C,
`2`=принудительно диск D. Добавлено ради плейлиста, где одна и та же
запущенная программа (`C/TOOLS/PLAYER.MC`) должна уметь грузить треки то
с одного диска, то с другого в рамках ОДНОГО запуска - `lastExecDisk`
сам по себе на это не способен, он фиксирован на весь запуск программы.
Пишется ПЕРЕД `COMMAND=LOAD` и остаётся в силе, пока не переписан
следующим `LOAD` - см. `C/TOOLS/PLAYER.MC::load_mod_from_playlist()`,
готовый рабочий пример, и раздел "Плейлист (PLAY.LST)" ниже.

Команда **1 (LOAD)** читает файл `NAME`, разбирает его (заголовок, 31
дескриптор сэмпла, order-таблицу, паттерны, PCM-данные сэмплов) и
одним вызовом кладёт результат в `SoundCard` (полностью заменяет
текущую песню, сбрасывает секвенсор в начало - на воспроизведение
нужно после этого явно послать `SoundCard.PLAY`, `LOAD` его не
запускает).

Пример - загрузить `SPACE_~1.MOD` и запустить:

    LDI A, 83   ; 'S'
    STA 0xF0001020
    LDI A, 80   ; 'P'
    STA 0xF0001021
    ; ... остальные буквы имени файла в NAME2-11, лишние - в 0 ...

    LDI A, 1
    STA 0xF0001040      ; COMMAND = LOAD

    LDA 0xF0001041       ; STATUS
    LDI B, 0
    CMP B
    JNZ mod_error

    LDI A, 1
    STA 0xF0001066      ; SoundCard COMMAND = PLAY

Полный рабочий пример - `C/DEMOS/MUSIC.ASM` (`cd demos`, затем
`exec music.asm`), песня - `C/DEMOS/SPACE_~1.MOD`.

## Gpu3D

3D-ускоритель, освещение и математический сопроцессор - ОДНО
устройство. Раньше их было три (`Gpu3D`/`Light3D`/`MathUnit`), у
каждого почти не было запаса адресов на рост; живое тестирование
показало, что такое дробление - плохая идея (ни одного свободного
регистра, три мелких устройства ради того, что по сути одна подсистема
"3D + математика"), поэтому их слили в одно - см.
`misty-zooming-bee.md`. Вся математика (матрицы модели/камеры,
перспективная проекция, растеризация с z-буфером, общая 16/32-битная
арифметика и тригонометрия) - на стороне C++. Процессору это не под
силу (нет даже нормального умножения без переполнения байта).
Ассемблеру видны только команды уровня "вот вершина", "нарисуй
треугольник", "нарисуй куб", "посчитай A+B", "покажи кадр" - вся
3D-сцена копится во ВНУТРЕННЕМ буфере `Gpu3D` (свой цветовой буфер
320x240 + свой z-буфер + маска "затронутых" пикселей) и передаётся в
`VideoCard` целиком одним вызовом по команде `PRESENT` (см. "Аппаратные
тайлы и скролл" выше про полный порядок слоёв - 3D рисуется НАД
тайлами, но ПОД спрайтами).

Адресный диапазон нарочно щедрый - 256 байт, `0xF0001100`-`0xF00011FF`
- хотя реально занята меньше половины. Смысл именно в запасе на рост
(больше источников света, протокол загрузки текстур богаче
нынешних фиксированных квадратов 32x32) без повторной перенумерации;
неиспользуемые смещения просто читаются как 0 и игнорируют запись.

Цвет - за каждой вершиной (Gouraud shading, как в PS1/N64), растеризатор
линейно интерполирует цвет (а для текстурированного треугольника -
семплированный тексель, см. "Текстуры" ниже) и глубину между тремя
вершинами треугольника. Цвет, переданный через `VR`/`VG`/`VB`, - это
БАЗОВЫЙ цвет треугольника, используется когда `VTEXTURE = 0`
(нетекстурировано, по умолчанию) - если перед `SUBMIT_VERTEX` задана
нормаль (`VNX`/`VNY`/`VNZ`), реально сохранённый цвет этой вершины -
базовый цвет, промодулированный светом (см. "Освещение" ниже); вершина
без заданной нормали (по умолчанию все нули) не получает направленного
освещения, только вклад ambient-уровня.

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 0-1 | VX_LOW/HIGH | X вершины, знаковое 16 бит, единицы модели |
| 2-3 | VY_LOW/HIGH | Y вершины |
| 4-5 | VZ_LOW/HIGH | Z вершины |
| 6 | VR | цвет вершины/куба, R (0-255) - игнорируется при текстуре |
| 7 | VG | цвет вершины/куба, G - игнорируется при текстуре |
| 8 | VB | цвет вершины/куба, B - игнорируется при текстуре |
| 9-11 | VNX/VNY/VNZ | нормаль СЛЕДУЮЩЕЙ вершины (см. "Освещение" ниже) |
| 12 | VU | текстурная U СЛЕДУЮЩЕЙ вершины (0-255 = 0.0-1.0) |
| 13 | VV | текстурная V СЛЕДУЮЩЕЙ вершины |
| 14 | VTEXTURE | слот текстуры СЛЕДУЮЩЕЙ вершины (0 = без текстуры, иначе 1-8 - см. "Текстуры" ниже) |
| 15 | COMMAND (запись = триггер) | 1=SUBMIT_VERTEX, 2=DRAW_TRIANGLE, 3=CLEAR, 4=PRESENT, 5=DRAW_CUBE |
| 16 | STATUS (только чтение) | 0=ok, 1=DRAW_TRIANGLE вызван без 3 накопленных вершин |
| 17-18 | CUBE_SIZE_LOW/HIGH | половина ребра следующего DRAW_CUBE, знаковое 16 бит |
| 19-24 | OBJ_X/Y/Z_LOW/HIGH | позиция объекта в мире, знаковое 16 бит |
| 25-30 | OBJ_YAW/PITCH/ROLL_LOW/HIGH | поворот объекта, градусы (знаковое 16 бит) |
| 31-36 | CAM_X/Y/Z_LOW/HIGH | позиция камеры в мире |
| 37-40 | CAM_YAW/PITCH_LOW/HIGH | поворот камеры (без крена) |
| 41-43 | LIGHT_DIR_X/Y/Z | направление света, мировое пространство |
| 44-46 | LIGHT_R/G/B | цвет/интенсивность света (0-255 на канал) |
| 47 | AMBIENT | уровень фоновой засветки (0-255) |
| 48-55 | *(зарезервировано)* | свободно |
| 56-63 | см. "Математика (16 бит)" ниже | |
| 64-77 | см. "Математика (32 бита)" ниже | |
| 78-96 | см. "Текстуры" ниже | |

`OBJ_*`/`CAM_*` действуют сразу по записи, без команды (как позиция
спрайта/скролл карты) - вращать объект или двигать камеру каждый кадр
должно быть дёшево (несколько `STA`, без лишнего байта-команды).

Все девять регистров направлений/нормалей (`VNX`/`VNY`/`VNZ`/
`LIGHT_DIR_*`) используют одну кодировку: знаковый байт, fixed-point
`/100.0` (100 = 1.0, `156` = -1.0, т.е. `256 - 100`). Одного байта
достаточно для единичного вектора - в отличие от мировых координат,
которым нужны все 16 бит, low/high пара тут не нужна. `VNX`/`VNY`/`VNZ`
нужно выставлять перед КАЖДЫМ `SUBMIT_VERTEX` (как `VR`/`VG`/`VB`) -
`Gpu3D::submitVertex()` берёт их снэпшот в момент вызова
`SUBMIT_VERTEX`.

Адреса: `0xF0001100` (VX_LOW) - `0xF00011FF` (конец резервного
диапазона).

### Команды

- **1 (SUBMIT_VERTEX)** - добавляет текущие `VX/VY/VZ/VR/VG/VB/VNX/
  VNY/VNZ` во внутренний накопитель вершин треугольника. Рассчитан на
  ровно 3 вершины - вызывающий код обязан слать `SUBMIT_VERTEX` три
  раза перед каждым `DRAW_TRIANGLE` (как `WRITE_PIXEL` у спрайтов/
  тайлов `VideoCard`, только без авто-инкремента индекса - тут всегда
  именно 3 вершины на треугольник).
- **2 (DRAW_TRIANGLE)** - применяет модельную матрицу (`OBJ_*` -
  перенос и повороты объекта) и матрицу камеры (`CAM_*`) к 3
  накопленным вершинам, проецирует в экранные координаты (320x240,
  фиксированный вертикальный FOV ~70°) и растеризует треугольник во
  ВНУТРЕННИЙ буфер `Gpu3D` - барицентрическая растеризация,
  Gouraud-интерполяция цвета, тест по z-буферу на пиксель (только
  более близкий пиксель перезаписывает более дальний). Треугольник, у
  которого хоть одна вершина оказалась "за камерой" (или ближе
  минимальной дистанции), целиком отбрасывается - честного клиппинга
  по плоскостям в v1 нет (упрощение: для выпуклых объектов вроде куба
  на типичной дистанции демо не критично). Не трогает `VideoCard`
  напрямую - только свой внутренний буфер.
- **3 (CLEAR)** - сбрасывает внутренний z-буфер (в "бесконечность") и
  маску "затронутых" пикселей - подготовка к новому кадру. Сам
  цветовой буфер трогать не нужно - непойманные в новом кадре пиксели
  просто не попадут в маску и не перекроют то, что уже нарисовано на
  `VideoCard` (фон/тайлы) при следующем `PRESENT`.
- **4 (PRESENT)** - одним вызовом (`VideoCard::setThreeDLayer`)
  передаёт видеокарте копию цветового буфера и маску "затронутых"
  пикселей за этот кадр. Первый `PRESENT` включает 3D-слой в
  композиции кадра видеокарты - до этого он просто пропускается,
  старые демо без 3D (`DEMO.ASM`, `SPRITES.ASM`, `TILEDEMO.ASM`) не
  видят разницы.
- **5 (DRAW_CUBE)** - аппаратный быстрый путь для очень частого случая
  осевого куба. Вместо того чтобы CPU слал 36 `SUBMIT_VERTEX` (12
  треугольников по 3 вершины, ~13 записей регистров на вершину - сотни
  обращений к шине на куб), он пишет только центр (`VX/VY/VZ`),
  половину ребра (`CUBE_SIZE_LOW/HIGH`) и базовый цвет (`VR/VG/VB`), а
  затем один раз вызывает `DRAW_CUBE`. `Gpu3D` сам строит все 8 углов и
  12 треугольников (с правильной осевой нормалью на каждую грань и
  полным UV-квадом `(0,0)-(1,1)` на каждую грань) и растеризует их через
  ТОТ ЖЕ пайплайн, что и `DRAW_TRIANGLE` - та же трансформация
  модели/камеры, то же освещение, тот же z-буфер. Если `VTEXTURE` в
  момент команды ненулевой, все 6 граней получают эту текстуру (см.
  "Текстуры" ниже) вместо цвета `VR/VG/VB`. Не трогает `pendingVertices`
  вообще - можно мешать `DRAW_CUBE` и ручные
  `SUBMIT_VERTEX`/`DRAW_TRIANGLE` в одном кадре. Не вызывает
  `CLEAR`/`PRESENT` сама - та же конвенция, что и у `DRAW_TRIANGLE`:
  вызывающий код чистит раз в начале кадра и показывает раз в конце,
  после отрисовки всего. Добавлено именно потому, что пол из множества
  отдельно отправляемых кубов (`C/DEMOS/CUBEWRLD.MC`) оказался
  слишком медленным для интерактивной игры - см.
  `misty-zooming-bee.md`.

### Освещение

Один направленный источник + фоновая засветка, считается один раз на
вершину (Gouraud - дальше интерполируется существующим растеризатором,
как и цвет всегда был): нормаль вершины поворачивается тем же поворотом
объекта, что и позиция вершины (но без переноса), затем

    brightness = AMBIENT/255 + (LIGHT_канал/255) * max(0, dot(мироваяНормаль, normalize(LIGHT_DIR)))
    итоговыйЦвет = clamp(базовыйЦвет * brightness, 0, 255)

применяется на каждый канал цвета. У вершины с нулевой нормалью (по
умолчанию) `dot(...) = 0` всегда, так что она получает только
ambient-вклад - удобно для объектов, которым освещение не важно.
`DRAW_CUBE` сам считает правильную осевую нормаль для каждой грани,
поэтому кубы всегда освещены корректно без ручной установки
`VNX`/`VNY`/`VNZ`.

### Математика (16 бит)

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 56-57 | MATH_A_LOW/HIGH | операнд A, знаковое 16 бит |
| 58-59 | MATH_B_LOW/HIGH | операнд B, знаковое 16 бит |
| 60 | MATH_COMMAND (запись = триггер) | 1=ADD, 2=SUB, 3=MUL, 4=DIV, 5=SIN, 6=COS, 7=SQRT |
| 61 | MATH_STATUS (только чтение) | 0=ok, 1=ошибка (деление на 0, либо `sqrt` из отрицательного A) |
| 62-63 | MATH_RESULT_LOW/HIGH (только чтение) | результат последней команды |

Не привязан конкретно к 3D-графике - любой программе, которой нужна
настоящая 16-битная арифметика или тригонометрия, можно им
воспользоваться (`MUL`/`DIV` процессора - только 8-битные, а `long` в
мини-C умеет лишь +/- на обычный `int`, см. "Тип `long`" ниже), как это
делает движение камеры в `CUBEWRLD.MC` (см. `C/DEV/LIB/GEOM3D.MC`).
`SIN`/`COS` трактуют `A` как угол в градусах (тот же формат, что у
`*_YAW`/`*_PITCH`/`*_ROLL` выше), `B` игнорируют; результат -
fixed-point `*100` (100 = 1.0), тот же масштаб, что у регистров
света/нормалей. `SQRT` использует только `A`, требует `A >= 0`.

Адреса: `0xF0001138` (MATH_A_LOW) - `0xF000113F` (MATH_RESULT_HIGH).

### Математика (32 бита)

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 64-67 | MATH32_A0-A3 | операнд A, знаковое 32 бита, little-endian (байт 0 - младший) |
| 68-71 | MATH32_B0-B3 | операнд B, знаковое 32 бита, little-endian |
| 72 | MATH32_COMMAND (запись = триггер) | 1=ADD, 2=SUB, 3=MUL, 4=DIV, 5=SQRT |
| 73 | MATH32_STATUS (только чтение) | 0=ok, 1=ошибка (деление на 0, либо `sqrt` из отрицательного A) |
| 74-77 | MATH32_RESULT0-3 (только чтение) | результат последней команды, little-endian |

Более широкий аналог 16-битного блока выше - для значений, которым
тесно в 16 битах (большие мировые координаты, дистанции, всё, что могло
бы переполниться). `SIN`/`COS` тут нет - углам никогда не нужен 32-битный
диапазон, они остаются на 16-битном блоке.

Адреса: `0xF0001140` (MATH32_A0) - `0xF000114D` (MATH32_RESULT3).

### Текстуры

Загрузка текстур живёт ВНУТРИ самого `Gpu3D`, а не в отдельном
устройстве - осознанно (см. `misty-zooming-bee.md`): `Gpu3D` сам
декодирует PNG-атлас (через `stb_image`, ту же библиотеку, что и
`PngLoader`) и вырезает 32x32-регионы в СВОЮ текстурную память
(`TEXTURE_SLOTS` = 8 слотов по 32x32 RGB каждый - пара десятков
килобайт, мелочь). Протокол намеренно один в один как у `PngLoader`
(см. его раздел выше): `LOAD` декодирует файл в закэшированный
RGBA-буфер, `EXTRACT` вырезает один квадрат 32x32 из этого кэша в
пронумерованный слот - один `LOAD` обслуживает много `EXTRACT` одного и
того же атласа без повторного декодирования.

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 78-89 | TEX_NAME0-11 | имя PNG-файла атласа, формат 8.3 |
| 90-91 | TEX_SRC_X_LOW/HIGH | X вырезаемого региона в атласе |
| 92-93 | TEX_SRC_Y_LOW/HIGH | Y вырезаемого региона |
| 94 | TEX_SLOT | целевой слот, 1-8 |
| 95 | TEX_COMMAND (запись = триггер) | 1=LOAD, 2=EXTRACT |
| 96 | TEX_STATUS (только чтение) | 0=ok, 1=файл не найден/ничего не загружено, 2=регион за границами, 3=неверный слот |

Адреса: `0xF000114E` (TEX_NAME0) - `0xF0001160` (TEX_STATUS).

Слот `0` зарезервирован под значение "без текстуры" - `VTEXTURE`
(смещение 14, выше по тексту описан как "зарезервировано") теперь
реально используется: выставляется на СЛЕДУЮЩУЮ отправляемую вершину
(как `VR`/`VG`/`VB`), вместе с `VU`/`VV` (смещения 12-13, текстурные
координаты 0-255 = 0.0-1.0). Текстурированный треугольник семплирует
слот, указанный в `VTEXTURE` (nearest-neighbor, без фильтрации - тот же
пиксель-артный стиль, что уже принят в проекте) по интерполированным
per-pixel `(u, v)`, и семплированный тексель ПОЛНОСТЬЮ заменяет базовый
цвет треугольника - освещение (ambient+diffuse) по-прежнему
умножается поверх, как и для обычного цвета. Нетекстурированная
вершина (`VTEXTURE = 0`, по умолчанию) рендерится в точности как
раньше - для существующих демок, не трогающих эти регистры, ничего не
меняется.

`DRAW_CUBE` (см. выше) тоже учитывает `VTEXTURE`: если он ненулевой в
момент команды, все 6 граней получают ОДНУ И ТУ ЖЕ текстуру (как сейчас
один цвет на весь куб), каждая грань развёрнута в полный UV-квад
`(0,0)-(1,0)-(1,1)-(0,1)`. `VR`/`VG`/`VB` для текстурированного куба
игнорируются - текстура полностью их заменяет.

Рабочий пример - `C/DEMOS/CUBEWRLD.MC`: грузит `TILES.PNG` один раз,
вырезает два тайла 32x32 в слоты 1 и 2, рисует оба слоя пола через
`draw_cube_at(..., texSlot)` (см. `C/DEV/LIB/GEOM3D.MC`).

### Пример

Нарисовать один треугольник (камера в `(0,0,-150)`, куб/объект в начале
координат без поворота - оба по умолчанию):

    LDI A, 106
    STA 0xF0001123      ; CAM_Z_LOW  (-150 в 16-битном доп. коде)
    LDI A, 255
    STA 0xF0001124      ; CAM_Z_HIGH

    LDI A, 3
    STA 0xF000110F      ; COMMAND = CLEAR

    ; вершина 0: (-30,-30,0), красная
    LDI A, 226
    STA 0xF0001100      ; VX_LOW
    LDI A, 255
    STA 0xF0001101      ; VX_HIGH
    ; ... аналогично VY_LOW/HIGH = -30, VZ_LOW/HIGH = 0 ...
    LDI A, 255
    STA 0xF0001106      ; VR = 255
    LDI A, 0
    STA 0xF0001107      ; VG = 0
    STA 0xF0001108      ; VB = 0
    LDI A, 1
    STA 0xF000110F      ; COMMAND = SUBMIT_VERTEX

    ; ... вершины 1 и 2 аналогично ...

    LDI A, 2
    STA 0xF000110F      ; COMMAND = DRAW_TRIANGLE

    LDI A, 4
    STA 0xF000110F      ; COMMAND = PRESENT

Полный рабочий пример - `C/DEMOS/CUBE3D.ASM` (`cd demos`, затем
`exec cube3d.asm`): вращающийся цветной куб (12 треугольников, по 2 на
грань) с UI-иконкой поверх (спрайт из `SPRITES.PNG`). Гораздо более
быстрый эквивалент через аппаратный примитив `DRAW_CUBE` плюс
освещённый пол (с заделом под текстуры), грузящийся из файла уровня -
`C/DEMOS/CUBEWRLD.MC` (обёртки мини-C - в `C/DEV/LIB/GEOM3D.MC`).

## Mouse

Относительное перемещение мыши (не абсолютная позиция курсора -
регистра "где сейчас курсор" нет, только "насколько сдвинулся") -
сделано под FPS-стиль "мышь крутит камеру", а не под указание на
элементы экрана.

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 0 | DELTA_X_SIGN (только чтение) | 0 = вправо, 1 = влево |
| 1 | DELTA_X_MAG (только чтение) | накопленный модуль перемещения по X с прошлого чтения (0-127); чтение обнуляет накопитель |
| 2 | DELTA_Y_SIGN (только чтение) | 0 = вверх, 1 = вниз |
| 3 | DELTA_Y_MAG (только чтение) | накопленный модуль по Y; чтение обнуляет накопитель |
| 4 | BUTTONS (только чтение) | бит 0 = левая кнопка, бит 1 = правая |
| 5 | CONTROL | бит 0 = захват (1 = спрятать курсор и держать его в центре окна, копя `DELTA_*` из движения, которое иначе увело бы курсор за пределы окна; 0 = обычный системный курсор, дельты не копятся) |

Перемещение передаётся как знак+модуль, а не знаковый байт - это
дружит с 8-битным `int` мини-C (беззнаковая арифметика с
переполнением): вызывающий код читает СНАЧАЛА `*_SIGN`, ПОТОМ `*_MAG`
(чтение модуля обнуляет накопитель, поэтому знак нужно прочитать ДО
модуля, не после), и прибавляет/вычитает модуль в зависимости от
знака вместо разбора «сырого» байта в дополнительном коде.

Адреса: `0xF0001075` (DELTA_X_SIGN) - `0xF000107A` (CONTROL).

## MatrixLoader

Обобщение `MapLoader` (см. выше) под "любую карту, описываемую
матрицей чисел" - карту уровня, сетку коллизий, что угодно - а не
конкретно тайловую карту `VideoCard`. Сам `MapLoader` не тронут
(`TILEDEMO.ASM`/`TSCROLL.MC`/`SNOW3D.MC` зависят от его точного
поведения); `MatrixLoader` - отдельное устройство с двумя отличиями:

- значения - полный диапазон байта 0-255 (не 0-127 - значение ячейки
  тут не обязательно индекс тайла);
- матрицу можно опрашивать по ячейкам с CPU уже после загрузки -
  `MapLoader` только толкает результат в `VideoCard` и не читается
  обратно вообще.

| Смещение | Регистр | Описание |
|----------|---------|----------|
| 0-11 | NAME0-11 | имя файла, формат 8.3 (та же конвенция, что у `Disk`/`PngLoader`/`MapLoader`) |
| 12 | COMMAND (запись = триггер) | 1=LOAD |
| 13 | STATUS (только чтение) | 0=ok, 1=файл не найден, 2=ошибка разбора |
| 14-15 | WIDTH_LOW/HIGH (только чтение) | ширина матрицы, выставляется LOAD |
| 16-17 | HEIGHT_LOW/HIGH (только чтение) | высота матрицы, выставляется LOAD |
| 18-19 | CELL_X_LOW/HIGH | X опрашиваемой ячейки |
| 20-21 | CELL_Y_LOW/HIGH | Y опрашиваемой ячейки |
| 22 | CELL_VALUE (только чтение) | значение в `(CELL_X, CELL_Y)`, считается при чтении; 0 если за границами |

Формат файла идентичен `MapLoader`: каждая строка - одна строка
матрицы, десятичные числа через пробел, все строки одной длины
(прямоугольная матрица), хвостовые пустые строки игнорируются - см.
"MapLoader" выше про точные правила разбора. `C/DEMOS/LEVEL.TXT` -
пример (сетка 8x8, значения 0-2 - см. `C/DEMOS/CUBEWRLD.MC`, который
трактует значение как высоту стопки кубов).

Адреса: `0xF000108D` (NAME0) - `0xF00010A3` (CELL_VALUE).

## KeyState

Зажата ли стрелка ПРЯМО СЕЙЧАС - сознательно отдельно от `Keyboard`
(см. выше), который устроен как очередь "для печати" (по байту на
нажатие) и плохо подходит для непрерывного движения: пока клавиша
зажата, Windows шлёт `WM_KEYDOWN` многократно (авто-повтор), а
программа, вычитывающая по одному байту очереди за кадр, отстаёт - хуже
того, каждый второй байт во время такой пачки - двухбайтовый префикс
extended-кода (см. раздел `Keyboard` выше), не совпадающий ни с одним
кодом клавиши вообще. Результат - те самые рывки при движении, что были
у `C/DEMOS/CUBEWRLD.MC` до появления этого устройства (см.
`misty-zooming-bee.md`) - очередь может выразить "произошло", но не
"зажато".

`KeyState` - однобайтовая битовая маска, обновляется `VideoConsole`
напрямую по `WM_KEYDOWN`/`WM_KEYUP` (не через очередь) - в любой момент
точно отражает, какие стрелки зажаты, без накопления и без потерь.
`Keyboard` при этом не тронут и по-прежнему используется, как и раньше
(навигация в FM/EDIT, разовые действия вроде Ctrl+Q) - читать `KeyState`
для движения и `KEYBOARD_DATA` для клавиши выхода в одном и том же
цикле - штатный приём, см. `C/DEMOS/CUBEWRLD.MC`.

| Бит | Клавиша |
|---|---|
| 0 | UP |
| 1 | DOWN |
| 2 | LEFT |
| 3 | RIGHT |
| 4-7 | зарезервировано |

Адрес: `0xF0001300` (1 байт, только чтение). Константы прелюдии (см.
"Встроенные константы регистров устройств" ниже): `KEYSTATE`,
`KEYSTATE_UP`, `KEYSTATE_DOWN`, `KEYSTATE_LEFT`, `KEYSTATE_RIGHT` -
например, `if (peek(KEYSTATE) & KEYSTATE_UP) { ... }`.

## Phys3D

Физический ускоритель - гравитация, AABB-объёмы для коллизий и
бесконечная опорная плоскость пола ("горизонт") - сознательно ОТДЕЛЬНОЕ
устройство от `Gpu3D`, не связанное с ним (см. `misty-zooming-bee.md` -
спарить их в будущем можно, но это отдельная задача). То же рассуждение,
что и у любого другого ускорителя в этой системе: процессору такая
математика не под силу, устройству - вполне, с любой нужной ему
внутренней точностью.

Ключевое архитектурное решение, извлечённое из истории производительности
самого `Gpu3D`: статичная геометрия уровня (кубы) описывается устройству
ОДИН РАЗ, при загрузке уровня (`DEFINE_BOX`, один вызов на каждый
сплошной кубик - как текстура или карта, "определи и забудь"), а не
пересылается заново каждый кадр. Через шину каждый кадр идёт только
одна команда `STEP` - "подвинь игрока на (dx,dy,dz), разреши коллизии" -
весь перебор боксов (потенциально сотни) считает C++ внутри устройства.

| Смещение | Регистр | Описание |
|---|---|---|
| 0-1 | GROUND_Y_LOW/HIGH | Y "горизонта" - бесконечной опорной плоскости пола, знаковое 16 бит |
| 2-3 | GRAVITY_LOW/HIGH | ускорение свободного падения, юниты/кадр², знаковое 16 бит |
| 4 | BOX_SLOT | индекс статичного бокса-коллайдера, 0-127 |
| 5-10 | BOX_X/Y/Z_LOW/HIGH | центр бокса, знаковое 16 бит |
| 11-13 | BOX_HALF_X/Y/Z | полуразмер бокса по каждой оси, 0-255 |
| 14 | BOX_COMMAND (запись = триггер) | 1=DEFINE (создать/обновить бокс в BOX_SLOT), 2=CLEAR_ALL |
| 15 | BOX_STATUS (только чтение) | 0=ok, 1=неверный слот |
| 16 | PLAYER_RADIUS | радиус коллизии игрока, 0-255 (игрок - СФЕРА, не AABB - см. ниже); смещения 17-18 не используются |
| 19-24 | PLAYER_X/Y/Z_LOW/HIGH | позиция игрока - пишется напрямую для спавна/телепорта (без проверки коллизий, как `OBJ_X` у `Gpu3D`); читается обратно после `STEP` как разрешённая позиция |
| 25-30 | MOVE_DX/DY/DZ_LOW/HIGH | желаемое смещение за этот кадр - выставляется перед `STEP` |
| 31 | GROUNDED (только чтение) | 1 = игрок стоит на полу/боксе |
| 32 | STEP_COMMAND (запись = триггер) | 1=STEP |
| 33 | STEP_STATUS (только чтение) | 0=ok |

До 128 статичных боксов (`MAX_BOXES`) - хватает на полностью сплошную
сетку размера `C/DEMOS/LEVEL.TXT` (64 клетки × 2 слоя стопки).

Адреса: `0xF0001200` (GROUND_Y_LOW) - `0xF0001221` (STEP_STATUS), внутри
зарезервированного диапазона в 256 байт (`0xF0001200`-`0xF00012FF`) -
та же конвенция щедрого запаса, что и у `Gpu3D`.

### STEP - алгоритм

1. Внутренняя (не регистр) `velocityY` копит `GRAVITY` на каждом шаге,
   обнуляется, если игрок стоял на опоре (`GROUNDED`) в начале шага.
2. Сфера игрока двигается СРАЗУ на полный вектор - `(MOVE_DX, MOVE_DY +
   velocityY, MOVE_DZ)` - не по одной оси за раз. Более ранняя версия
   разрешала X, затем Z, затем Y раздельно (приём "подвинь-проверь-
   вытолкни", которым пользуется большинство простых 3D-платформеров) -
   при движении по диагонали в угол бокса это могло на кадр "продавить"
   камеру частично внутрь геометрии, потому что каждый проход по своей
   оси видит только одномерное пересечение, а не настоящую точку
   контакта.
3. Для каждого активного бокса: находим ближайшую точку на боксе к
   центру сферы (покоординатный clamp), и если расстояние от неё до
   центра меньше `PLAYER_RADIUS` - выталкиваем центр вдоль ЭТОГО
   направления (настоящее направление проникновения, что в грань, что в
   угол) на `radius - distance` **плюс небольшой запас** (пара юнитов),
   чтобы сфера никогда не останавливалась ровно впритык к грани - без
   этого камера может оказаться настолько близко к грани, что при
   повороте видна изнанка куба (в растеризаторе `Gpu3D` нет backface
   culling, см. его раздел выше - тот же класс артефакта, что и
   z-fighting между соседними кубами, там решённый похожим небольшим
   зазором). Выталкивание, направленное преимущественно "вверх" (см.
   конвенцию знака выше), считается приземлением - `GROUNDED=1`,
   `velocityY=0`, независимо от того, бокс это сверху или плоскость
   пола снизу.
4. Отдельно - та же проверка с запасом против плоскости `GROUND_Y`.
5. Записываются разрешённые `PLAYER_X/Y/Z` и `GROUNDED`.

Полная 3D-коллизия, а не только "стены" - на бокс можно "приземлиться"
сверху точно так же, как на плоскость пола; примитив "блокировать
только движение вбок" был бы частным случаем этого, а не наоборот. Сами
боксы остаются AABB (три полуразмера) - сфера только у ИГРОКА, именно
это и делает трюк с ближайшей точкой простым известным тестом
sphere-vs-AABB.

Рабочий пример - `C/DEMOS/CUBEWRLD.MC` (обёртки мини-C -
`phys_define_box()`/`phys_step()`/др. в `C/DEV/LIB/PHYS3D.MC`): один
бокс на каждый блок стены при загрузке (пол отдельного бокса не
требует - его везде покрывает плоскость `GROUND_Y`), затем каждый кадр
один `STEP` с желаемым горизонтальным смещением, а разрешённая позиция
копируется в `CAM_X/Y/Z` у `Gpu3D` - камера И ЕСТЬ игрок.

# 10. Прерывания

Процессор поддерживает одну линию запроса прерывания
(IRQ), общую для всех устройств на шине. У прерывания нет
приоритета и вектора — обработчик всегда один, и если
источников несколько, он сам должен определить, какое
устройство его вызвало (опросив его регистры).

## Разрешение прерываний

Прерывания запрещены по умолчанию (после reset). Их нужно
явно разрешить инструкцией `EI` и можно запретить `DI`.

## Обработчик прерывания

Обработчик обязан начинаться по фиксированному адресу
`0x00000005`. Поскольку выполнение всегда начинается с адреса
`0x00000000`, прикладная программа, использующая прерывания,
должна начинаться с таблицы переходов:

    JMP main
    JMP irq_handler

    main:
        ; основная программа

    irq_handler:
        ; обработчик прерывания
        RETI

Первые 5 байт (`JMP main` — опкод + 4-байтный адрес) уводят
выполнение от вектора прерывания к реальному началу программы.
Вторые 5 байт (по адресу `0x00000005`) — это `JMP irq_handler`,
на который процессор перейдёт при прерывании.

## Что происходит при прерывании

Между выполнением инструкций процессор проверяет, разрешены
ли прерывания и запрашивает ли что-нибудь на шине прерывание.
Если да:

1. На стек кладутся: `PC` (адрес прерванной инструкции, 4 байта),
   затем `FLAGS` (1 байт).
2. Прерывания автоматически запрещаются (как `DI`).
3. `PC` устанавливается в `0x00000005`.

`RETI` в конце обработчика снимает `FLAGS` и `PC` со стека
в обратном порядке и заново разрешает прерывания.

Регистры `A`, `B`, `C`, `D` процессор не сохраняет —
обработчик обязан сохранить через `PUSH`/`POP` те регистры,
которые он использует, и восстановить их перед `RETI`.

## Пример: обработчик прерывания от таймера

    JMP main
    JMP irq_handler

    main:

        LDI A, 0xE8
        STA 0xF0000002      ; CMP_LOW  = 0xE8
        LDI A, 0x03
        STA 0xF0000003      ; CMP_HIGH = 0x03  (порог = 1000)
        LDI A, 1
        STA 0xF0000004      ; включить таймер

        EI

    loop:
        JMP loop

    irq_handler:

        PUSH A

        LDI A, 1
        STA 0xF0000004      ; подтвердить прерывание, таймер остаётся включён

        POP A

        RETI

# 12. Мини-C

Писать сложную логику прямо на ассемблере (раздел 3) больно - нет
переменных с именами вместо адресов, нет структурного `if`/`while`,
каждое ветвление - ручные `JMP`/`JZ`/`CMP`. Мини-C - урезанный
Си-подобный язык поверх этого же ассемблера: компилятор (`Compiler.h`/
`.cpp`) переводит текст на мини-C в обычный ASM-текст (тот же
синтаксис, что и выше в этом файле) и отдаёт его тому же `Assembler`,
что собирает `.asm` - дальше всё как с обычной программой: `build
ИМЯ.MC` кладёт `ИМЯ.RUN` рядом (см. `BUILD`/`LOAD_RAW` в разделе
"Disk"), и его можно запустить именем файла без расширения, как любой
`.RUN`.

Язык сознательно урезан под реальные возможности этого CPU (8-битный
АЛУ, нет адресации "стек+смещение" для локальных переменных, нет
инструкции "регистр в регистр" кроме `LDHL`) - это не стилистический
выбор, а прямое следствие набора инструкций из раздела 3.

## Типы и переменные

Основной тип - `int`, беззнаковый 8-бит (как регистры CPU).
Переполнение молча заворачивается, как и везде в этом ассемблере.
Есть ещё `long` - 16-битный скаляр с сознательно узким набором
поддержанных операций (см. "Тип `long`" ниже), и `string` -
двумерный, "массив строк" фиксированной формы (см. "Тип `string`"
ниже) для случаев вроде плейлиста, где обычному `int arr[N]` не
хватает 255-элементного потолка индекса.

Переменных **только глобальные** - настоящих локальных переменных со
стек-кадром не бывает (у CPU нет адресации "SP+смещение"). `int x;`
и внутри `main()`/любой функции, и на верхнем уровне файла - в обоих
случаях это одна и та же именованная ячейка памяти (`x: DB 0` в
сгенерированном ASM), просто с той разницей, что внутри функции можно
сразу присвоить начальное значение: `int x = 5;`.

Массивы фиксированного размера - только на верхнем уровне:

    int arr[16];

Индекс обычно 8 бит (0-255), `arr[i]` работает и на чтение, и на
запись. Реализовано на тех же приёмах, что `cmdbuf`/`NAME` в
`SHELL.ASM`: `LDHL` на базовый адрес массива + `INCHL` в цикле нужное
число раз (отдельная подпрограмма `__mc_hladd`, которую компилятор сам
дописывает в конец программы, если массивы вообще использовались).
Индексация переменной типа `long` (см. "Тип `long`" ниже) поднимает
этот потолок до 65535 элементов - `arr[16]` по-прежнему резервирует
ровно 16 байт, так что размер самого массива никогда не был ограничен
255 - ограничено было только то, насколько далеко мог дотянуться
обычный `int`-индекс.

### Тип `long`

    long i;
    i = 0;
    while (i < 2000) {
        bigArr[i] = что-то;
        i = i + 1;
    }

`long` - 16-битный беззнаковый скаляр (0-65535), добавлен специально
для того, чтобы индексы массивов и счётчики циклов могли уходить за
255-элементный потолок обычного `int`-индекса, но при этом не давать
8-битному АЛУ процессора никакой настоящей 16-битной арифметики.
Внутри `long NAME;` резервирует две ячейки - `NAME` (младший байт) и
скрытую `NAME__hi` (старший, отдельная метка - у ассемблера нет
арифметики операндов вида "метка+1"), - тот же приём с переносом через
`ADC`/`SBC`, что уже использует `__mc_screen_offset` для `y*80+x` (см.
"Маппированные массивы" выше).

Намеренно поддержан только узкий набор форм - всё остальное даёт
ошибку компиляции (`Мини-C: строка N: 'NAME' - long (16 бит), нельзя
использовать напрямую как обычное значение...`), а не тихо усечённый
или неверный результат:

- `long NAME;` - объявление (только глобальное, как и `int`; в v1 нет
  `long`-параметров функций и `long`-возврата).
- `NAME = <intExpr>;` - присваивает выражение из диапазона `int`,
  расширяя нулём (старший байт становится 0).
- `NAME = NAME + <intExpr>;` / `NAME = NAME - <intExpr>;` -
  единственная поддержанная арифметика: инкремент/декремент на
  обычное `int`-значение, перенос между двумя байтами через `ADC`/
  `SBC`. Любая другая комбинация (`long + long`, `*`, `/`, `%`,
  побитовые операции, `long` справа от `+`/`-`) - ошибка компиляции.
- Сравнения в `if`/`while` - `NAME < intExpr`, а также `NAME <
  другойLong` (и `<=`, `>`, `>=`, `==`, `!=`) - сначала сравниваются
  старшие байты, младшие - только при равенстве, та же двухшаговая
  цепочка, что сделал бы человек вручную.
- `arr[NAME]` - использование голой `long`-переменной как индекса
  массива, см. "Маппированные массивы" выше. Индексом может быть
  только голый идентификатор `long` - составное выражение вроде
  `arr[i + 1]`, где `i` - `long`, даёт ошибку компиляции, а не тихое
  усечение.

Использование `long`-переменной напрямую как обычного 8-битного
значения (просто как выражение, аргумент функции, `print_char` и
т.п.) - тоже ошибка компиляции: неявного сужения нет, поскольку тихое
отбрасывание старшего байта - ровно тот класс бага, ради
предотвращения которого этот тип и существует.

Ни один инструмент/демка в проекте пока не использует `long` для
собственных данных (буфер `EDIT.MC`, например, по-прежнему устроен по
схеме "один массив на строку" - см. "Пример: VIEW.MC / DISKIO.MC"
ниже) - тип добавлен на будущее, чтобы код, которому понадобится
массив побольше (более длинный буфер текста, бо́льший уровень и т.п.),
не изобретал свой одноразовый 16-битный костыль.

### Тип `string`

    string playlist[16][36];
    playlist[2][0] = 65;
    ch = playlist[2][0];
    print_string(4, 5, playlist, 2);

`string ИМЯ[COUNT][WIDTH];` - COUNT строк по WIDTH байт каждая (обычный
`int`, всегда собственное хранилище - мапированного варианта, в отличие
от `int arr[N] = адрес;`, у строк нет, им нечего окном показывать в
MMIO). Решает ту же проблему, что уже решает `long` для одномерных
массивов - только для ДВУМЕРНОЙ индексации. Обычный `arr[i]` считает
адрес как `база + i` через `__mc_hladd` - тот жёстко обнуляет старший
байт получившегося смещения (см. выше, `long` как индекс), поэтому `i`
не может быть больше 255: не мягкое ограничение на размер массива, а
жёсткое ограничение на то, что `__mc_hladd` вообще способен посчитать.
Из-за этого "массив строк" (например, до 16 путей плейлиста по 36 байт
каждый - `16*36=576`) не влезал бы ни в один `int arr[N]` разом - только
россыпью из N параллельных массивов одинаковой формы плюс `if`-каскад,
выбирающий нужный по рантайм-индексу (готовый пример именно этого
приёма для строк ЭКРАНА - `row0[32]`...`row13[32]` в `C/DEV/SRC/
SNAKE.MC`, `set_cell(x,y,ch)`).

`string` вместо этого считает офсет `row*WIDTH+col` тем же приёмом, что
`__mc_screen_offset` уже считает `y*80+x` (см. "Экранные встроенные
функции" ниже) - НЕ через 8-битный `MUL` (переполнился бы уже при
скромных COUNT/WIDTH), а циклом `ADD`/`ADC`, копящим настоящую
16-битную пару байт, и одним `ADDHL` в конце (внутренний помощник
`__mc_str_offset`, параметризованная копия `__mc_screen_offset` - WIDTH
берётся из объявления КОНКРЕТНОГО string-массива, а не жёстко зашит,
как экранные 80). `playlist[i][j]` - и чтение, и запись - работает при
любых `i` (до 255) и `j` (до 255) в пределах реально объявленных COUNT/
WIDTH; выход за объявленные границы, как и у обычных массивов, не
проверяется в рантайме.

`print_string(x, y, ИМЯ, index)` - встроенная функция, печатает строку
`ИМЯ[index]` начиная с `(x, y)`, останавливаясь на первом нулевом байте
или после WIDTH символов (что раньше) - рантайм-аналог `print_str`, но
для содержимого, вычисленного в рантайме (в файле, введённого
пользователем и т.п.), а не для строкового литерала, известного на
этапе компиляции. `ИМЯ` резолвится в кодогене (как и первый аргумент
`str_copy()`), `index` - обычное рантайм-`int`-выражение.

Сознательно НЕ добавлены: конкатенация, сравнение строк, мапированный
вариант (`= адрес`) - ничего из этого не нужно единственному
существующему потребителю (`C/TOOLS/PLAYER.MC`, плейлист - см. "Плейлист
(PLAY.LST)" ниже) и было бы спекулятивной полнотой без реального
использования. Готовый рабочий пример - `C/TOOLS/PLAYER.MC`:
`playlist[16][36]`, заполняется `load_playlist()`, читающим
`PLAY.LST` через `DISKIO.MC`, показывается `run_playlist_menu()`/
`render_playlist()` через `print_string()`.

### Маппированные массивы

    int row3[32] = 0xF0000007 + 80*4;

Тот же синтаксис `int имя[размер]`, плюс необязательное `= адрес`
(адрес - тоже константа времени компиляции, как у `poke`/`const`).
Без инициализатора массив, как обычно, получает собственную память
(`DB` в конце программы). С инициализатором - никакой собственной
памяти не резервируется: `arr[i]` вместо `LDHL <внутренняя метка>`
делает `LDHL <адрес>` - то есть массив становится "окном" в уже
существующую память (обычно - в MMIO-регистр какого-то устройства).

Пригодится там, где `poke`/`peek` не годятся, потому что адрес
известен только в рантайме: `poke`/`peek` жёстко требуют адрес-
константу (раздел "poke/peek" выше) - это можно обойти, ЕСЛИ базовый
адрес известен заранее, а меняется только смещение, - именно так
устроен любой массив. Пример - запись в произвольную ячейку строки
экрана Text VRAM (адрес `0xF0000007 + y*80 + x`, раздел 9): базовый
адрес строки - константа, а `x` внутри строки - обычный рантайм-
индекс. Из-за 8-битного индекса (`arr[i]` не бывает больше 256
элементов) под каждую строку экрана нужен отдельный маппированный
массив - готовый пример на несколько строк подряд и выбор нужной по
`if`-каскаду - `C/DEMOS/SNAKE.MC` (см. ниже).

## Функции

    int add(int a, int b) {
        return a + b;
    }

Параметры - на самом деле скрытые глобальные переменные с
"мангленным" именем (`add__a`, `add__b`), которые вызывающий код
заполняет прямо перед `CALL add`. **Рекурсия не поддерживается** -
рекурсивный вызов затёр бы параметры внешнего вызова, поскольку это
одна и та же глобальная ячейка, а не новый кадр стека.

Программа обязана содержать `int main() { ... }` - именно с неё
начинается выполнение (`JMP main` - первая инструкция сгенерированной
программы, независимо от порядка функций в файле). `return выражение;`
кладёт значение в `A` и делает `RET` - если `main`/функция доходит до
конца тела без явного `return`, компилятор сам вставляет `LDI A, 0` +
`RET`.

## Управляющие конструкции

`if`/`else`, `while`, `for` (сахар над `while` - `for (init; cond;
post) тело`, все три части обязательны):

    if (x > 3) {
        x = 100;
    } else {
        x = 200;
    }

    while (i < 5) {
        sum = sum + i;
        i = i + 1;
    }

    for (i = 0; i < 4; i = i + 1) {
        sum = sum + i;
    }

## Операторы

    +  -  *  /  %  &  |  ^  ~  <<  >>
    == != < > <= >=
    && ||
    =

Почти все ложатся 1-в-1 на уже существующие опкоды (`ADD`/`SUB`/
`MUL`/`DIV`/`MOD`/`AND`/`OR`/`XOR`/`NOT` - раздел 3). Сдвиги (`<<`/
`>>`) реализованы циклом из `SHL`/`SHR` (сами по себе они сдвигают
только на 1 бит - раздел 3), поэтому сдвиг на переменную величину
работает, но стоит дороже, чем на константу.

Сравнения (`==`/`!=`/`</`>`/`<=`/`>=`) материализуют результат как
`0`/`1` в `A` через `CMP` и пару условных переходов - то же самое
"полноценное беззнаковое сравнение через ZERO+CARRY", что описано в
разделе 2 про `FLAGS`. `&&`/`||` - с коротким замыканием (правый
операнд не вычисляется, если левый уже решил результат).

## poke/peek - прямой доступ к памяти и MMIO

    poke(адрес, значение)   ; memory[адрес] = значение
    peek(адрес)             ; вернуть memory[адрес]

Позволяет работать с любым регистром любого устройства (раздел 9) -
видеокартой, звуком, диском, 3D - без специальных обёрток в языке.

**`адрес` обязан быть константой времени компиляции** (число,
`0x`-литерал, или `const`, см. ниже, в том числе простая арифметика
над ними, вычисляемая компилятором заранее) - это ограничение ISA,
не языка: у CPU нет инструкции "загрузить HL/адрес из регистра",
`LDA`/`STA` принимают только литерал или метку, резолвящуюся во время
сборки (раздел 3, `LDA`/`STA`). Произвольный адрес, вычисленный в
runtime, положить в `LDA`/`STA` физически нельзя.

## const

    const VRAM = 0xF0000007;

Именованная константа времени компиляции - удобно для адресов
регистров устройств вместо голого хекса в каждой программе. Не
занимает памяти - везде, где встречается имя, компилятор подставляет
число.

## Встроенные константы регистров устройств (прелюдия)

Перед компиляцией вашего исходника компилятор незаметно подставляет
перед ним фиксированный блок объявлений `const`/маппированных массивов
для регистров, которые нужны почти любой графической/тайловой программе
- `Keyboard`, `Clock`, `VideoCard` (фон, аппаратные спрайты, тайловый
скролл), `ConsoleLayer`, `PngLoader`, `MapLoader`, `Mouse`,
`MatrixLoader`, `KeyState` (что делает каждый регистр - см. их разделы выше).
Объявлять их самому не нужно - они уже есть, с префиксом устройства в
имени, чтобы одинаковые имена регистров у разных устройств (`COMMAND`,
`STATUS`) не конфликтовали:

    KEYBOARD_DATA, KEYBOARD_CONTROL
    CLOCK_LOW, CLOCK_HIGH
    VIDEOCARD_X_LOW .. VIDEOCARD_STATUS                 (фон)
    VIDEOCARD_SPRITE_INDEX .. VIDEOCARD_SPRITE_STATUS   (аппаратные спрайты)
    VIDEOCARD_SCROLL_X_LOW .. VIDEOCARD_SCROLL_Y_HIGH   (тайловый скролл)
    CONSOLE_VISIBLE
    PNGLOADER_NAME0, PNGLOADER_SRC_X_LOW .. PNGLOADER_TILE_INDEX
    MAPLOADER_NAME0, MAPLOADER_COMMAND, MAPLOADER_STATUS
    MOUSE_DELTA_X_SIGN .. MOUSE_CONTROL
    MATRIXLOADER_NAME0 .. MATRIXLOADER_CELL_VALUE
    KEYSTATE, KEYSTATE_UP, KEYSTATE_DOWN, KEYSTATE_LEFT, KEYSTATE_RIGHT
    EXEC_CHILD_DISK
    CMD_ARGS_LEN

`Gpu3D` (он же теперь и освещение, и математический сопроцессор 16/32
бита, см. его раздел выше) и `Phys3D` - исключения: их регистры НЕ в
прелюдии, они объявлены вручную как обычные `const` в библиотеках
`C/DEV/LIB/GEOM3D.MC` и `C/DEV/LIB/PHYS3D.MC` (`#include "GEOM3D.MC"`/
`#include "PHYS3D.MC"` - см. "#include" ниже, там же про несколько
`#include` в одном файле) - адреса стабильны, при желании их несложно
добавить в прелюдию так же, как остальные, но это сознательно не
сделано, чтобы прелюдия оставалась компактной и покрывала устройства,
нужные почти любой программе, а не специфичные для 3D/физики.

Вместе с ними подставлены три готовых маппированных массива поверх
буферов `NAME0-11` - `pngLoaderName`/`mapLoaderName`/`matrixLoaderName`
(`int ...[12] = ...;`), рассчитанные на использование прямо со
`str_copy()` (см. ниже) вместо побайтной записи имени файла устройства.
Ещё один, `cmdArgs[16]`, -
маппированный массив поверх `CMD_ARGS_TEXT` (см. "Аргументы командной
строки" в разделе "Disk" выше) - текст аргумента после имени программы
на командной строке, или то, что вызывающая программа положила туда
сама перед `exec_child()`.

Если ваша собственная программа объявит `const`/массив под тем же
именем - выигрывает ваше объявление: в компиляторе нет проверки на
повторное объявление (см. "const" выше, это обычная карта "последнее
присваивание побеждает"), а ваше объявление компилируется ПОСЛЕ
прелюдии. Номера строк в ваших собственных сообщениях об ошибках при
этом никак не сдвигаются: прелюдия лексуется как отдельный чанк со
своим собственным счётчиком строк, заново начинающимся с 1, независимо
от вашего файла - тот же приём использует `#include` (см. ниже) для
библиотечных файлов.

## Экранные встроенные функции

Прямая работа с Text VRAM/TextAttr через `poke()` требует адрес-
константу (см. "poke/peek" выше) - для КОНКРЕТНОЙ, известной заранее
ячейки экрана этого достаточно, но для "нарисовать что-то в точке
(x, y), где x/y - переменные" уже нет: адрес `0xF0000007 + y*80 + x`
тогда вычисляется в рантайме, а `poke`/`peek` рантайм-адреса
принципиально не умеют. Поэтому экран - **единственное** исключение,
встроенное в язык напрямую (как когда-то `poke`/`peek`), а не
собираемое пользователем вручную из массивов:

    clear_screen();               // очищает и текст, и цвет (Text VRAM + TextAttr CLEAR)
    print_char(x, y, ch);         // печатает символ ch (0-255, CP866 - раздел 9) в ячейку (x, y)
    print_str(x, y, "текст");     // печатает строковый литерал начиная с (x, y), без переноса строк
    print_string(x, y, arr, i);   // печатает СТРОКУ arr[i] (см. "Тип string") - рантайм-аналог print_str
    set_color(x, y, fg, bg);      // цвет ячейки (x, y): fg/bg - 0-15 (см. "TextAttr", раздел 9)

`x` (0-79), `y` (0-24), `ch`/`fg`/`bg` - обычные `int`-выражения,
могут быть переменными, а не только константами - именно это
отличает их от прямого `poke()`. `y*80` считается не одним `MUL`
(переполнился бы уже при `y >= 4`), а циклом дешёвых `ADD`/`ADC` по 80
за итерацию, плюс один `ADDHL` в конце, чтобы применить получившееся
смещение к `HL` за один шаг (см. раздел 3, `ADDHL`) - компилятор сам
добавляет этот код (`__mc_screen_offset`) в сгенерированную программу,
если хоть раз встретил одну из этих функций.

`print_str` - единственное место в языке, где допустим строковый
литератор `"..."` (без экранирования спецсимволов в v1 - только
печатаемые ASCII-байты) - его содержимое компилятор кладёт как `DB`-
данные и проходит их в рантайм-цикле, вызывая для каждого символа тот
же путь, что и `print_char`, увеличивая `x` на единицу за символ - не
переносит строку сам, для новой строки текста нужен отдельный вызов с
другим `y`.

## Запуск дочерней программы: exec_child()

    poke(0x0000000F, diskId);   // EXEC_CHILD_DISK - какой диск (0=C,1=D) держит NAME
    exec_child();

Запускает `*.RUN`-программу ИЗНУТРИ уже выполняющейся программы - как
системный вызов резидентного `SHELL.ASM`, а не голый прыжок в
песочницу. Компилятор эмитит `CALL 0x0000000A` - фиксированный низкий
адрес, который `SHELL.ASM` патчит на свою процедуру
`shell_exec_child` при старте (тем же способом, что и вектор
прерывания `0x00000005` - см. `SHELL.ASM::main`). Сама программа не
решает, по какому адресу и какой командой диска (`15`-`18`,
`LOAD_CHILD`, см. раздел "Disk") грузить дочерний `*.RUN` - только
кладёт `NAME` на нужный диск и говорит `shell_exec_child`, какой это
диск, через `EXEC_CHILD_DISK` (`0x0000000F`, `0`=C, `1`=D). Управление
вернётся сюда же, когда дочерняя программа дойдёт до своего `RET`
(гарантированно происходит в конце любой функции Мини-C, включая
`main()` - компилятор никогда не генерирует `HLT`).

`shell_exec_child` ведёт учёт текущей глубины вложенности
(`execDepth`, резидентная переменная `SHELL.ASM`, начинается с `1` -
обычная программа "shell → X", ещё не звавшая `exec_child()`) и по
ней выбирает адрес и команду диска для СЛЕДУЮЩЕГО уровня - до 4
дополнительных уровней (`execDepth` `2`-`5`, см. раздел "Disk",
`LOAD_CHILD`). Перед входом во вложенный уровень явно делает `DI`
(гарантия известного состояния прерываний на границе вызова) -
дочерняя программа сама решает, звать ли `EI`, и обязана сделать `DI`
перед своим `RET` (см. `CUBE3D.ASM`/`TILEDEMO.ASM`/`MUSIC.ASM`). Перед
`CALL` также обнуляет `lastKey` (`0x00010001`) - это ОБЯЗАТЕЛЬНО:
дочерняя программа обычно сама сравнивает `lastKey` с кодом клавиши в
своём цикле опроса (например `== 17` для Ctrl+Q, как в
`MUSIC.ASM`/`music_loop`), и без сброса увидела бы СТАРОЕ значение,
оставшееся от предыдущего запуска (своего или чужого), и вышла бы
мгновенно, ни разу не дождавшись настоящего нажатия - а несъеденная
клавиша, которую пользователь нажимает уже после этого, "проваливается"
в того, кто вызвал `exec_child()` (например, `FM.MC` тоже увидит тот же
Ctrl+Q через `peek()` и выйдет сам). Та же логика и по той же причине
- в `cmd_run`/`cmd_exec_run` (обычный `exec`/`run` из шелла, не через
`exec_child()`).
Нужен ли `LOAD_CHILD` вообще (а не прямой `CALL` в песочницу самой
вызывающей программы) - из-за того, что вызывающая программа
(например, файловый менеджер `FM.MC`) сама выполняется по `0x00002000`
- если бы дочернюю программу грузили туда же, загрузка затёрла бы код,
который в этот момент как раз исполняется; а раз у каждого уровня
вложенности - свой отдельный адрес (не один общий "детский"), настоящая
многоуровневая вложенность (программа → дочерняя → внучатая → ...)
работает сама собой, без переделок компилятора.

Готовый пример - `C/TOOLS/FM.MC`: `Enter` на файле `*.RUN` в списке
копирует его имя в `NAME`, кладёт диск в `EXEC_CHILD_DISK`, затем
вызывает `exec_child()`; после возврата - `clear_screen()` и полная
перерисовка обеих панелей (дочерняя программа наверняка использовала
экран под себя).

Чтобы заодно передать дочерней программе аргумент (см. "Аргументы
командной строки" в разделе "Disk" выше) - заполните `cmdArgs`/
`CMD_ARGS_LEN` сами перед вызовом `exec_child()` - `shell_exec_child`
этот канал не трогает, только ваш собственный код:

    cmdArgs[0] = 84; cmdArgs[1] = 88; cmdArgs[2] = 84;   // "TXT" - или str_copy(cmdArgs, "...")
    poke(CMD_ARGS_LEN, 3);
    poke(EXEC_CHILD_DISK, diskId);
    exec_child();

Готовый пример - `F3` в `C/TOOLS/FM.MC` (`view_selected_file()`):
кладёт `VIEW.RUN` в `NAME` (программу для запуска) и имя ВЫДЕЛЕННОГО
файла в `cmdArgs` (аргумент) - две разные строки одновременно, именно
поэтому и нужен отдельный от `NAME` канал.

## Звук и музыка: mod_load()/sound_*()

    if (mod_load("SPACE_~1.MOD") != 0) { return 1; }   // STATUS: 0=ok,1=не найден,2=плохой формат,3=битый
    sound_play();
    sound_stop();
    sound_pause();
    sound_resume();
    sound_set_volume(255);   // 0-255, общая громкость

Эргономичные обёртки над `ModLoader`/`SoundCard` (см. разделы выше) -
до их появления достучаться до них можно было только голым `poke()`/
`peek()` с литеральными MMIO-адресами, выписанными вручную.

`mod_load(строка)` интересно сравнить с `print_str`: `print_str`
нужен настоящий РАНТАЙМ-цикл, потому что координаты назначения (`x`,
`y` в Text VRAM) бывают рантайм-переменными. У `mod_load`, напротив,
адрес назначения всегда один и тот же - фиксированный диапазон
`NAME0-31` у `ModLoader`, компилятивно-константный адрес, и точка.
Поэтому компилятор вообще не эмитит цикл: он разворачивает строковый
литерал в плоскую последовательность пар `LDI A,<байт>; STA <адрес>`,
по паре на символ, НА ЭТАПЕ КОМПИЛЯЦИИ, дописывает нулями до 32 байт,
затем эмитит `LDI A,1; STA 0xF0001040` (COMMAND=LOAD) и `LDA
0xF0001041` (STATUS остаётся в `A` - результат всего выражения).
Никакого рантайм-цикла - значит, никаких рантайм-затрат сверх
фиксированной последовательности записей - дешевле, чем механизм
`print_str`, а не просто короче записанный тот же приём. Литерал
длиннее 32 символов - ошибка компиляции.

`sound_play()`/`sound_stop()`/`sound_pause()`/`sound_resume()` не
принимают аргументов - каждый это просто `LDI A,<код>; STA
0xF0001066` (COMMAND у `SoundCard`, см. выше), тот же приём, что и у
`clear_screen()`. `sound_set_volume(v)` вычисляет `v` в `A` и кладёт
его в `0xF0001068` (VOLUME у `SoundCard`) - тот же приём, что и у
`set_color()`, только один регистр вместо четырёх.

Чтение новых регистров визуализации (`CHANNEL0-3_VOLUME`/`ROW`/
`ORDER_POS`) вообще не требует нового builtin'а - маппированный
массив поверх `CHANNEL0-3_VOLUME` (как игровое поле у `SNAKE.MC`) или
обычный `peek()` для `ROW`/`ORDER_POS` уже делают всё нужное, раз эти
адреса сами по себе компилятивно-константны. См. "SoundCard" выше и
`C/DEMOS/MUSIC2.MC` ниже - полный пример.

## str_copy() - копирование строкового литерала в маппированный массив

    str_copy(pngLoaderName, "TILES.PNG");
    poke(PNGLOADER_COMMAND, 1);          // LOAD - str_copy() сам команду не триггерит
    if (peek(PNGLOADER_STATUS) != 0) { ... }

Копирует строковый литерал в маппированный массив (`int arr[N] =
адрес;`, см. "Маппированные массивы" выше) на этапе компиляции - тот же
приём, что и `mod_load` (плоская последовательность пар `LDI A,<байт>;
STA <адрес>`, дозаполненная нулями до конца), только обобщённый на
ЛЮБОЙ маппированный массив, а не только фиксированный `NAME0-31` у
`ModLoader`. Рассчитан на запись имени файла устройства одной строкой
вместо одного `poke()`/присваивания элементу массива на символ -
например, заполнение `NAME`-буфера `PngLoader`/`MapLoader` через
готовые `pngLoaderName`/`mapLoaderName` из прелюдии (см. "Встроенные
константы регистров устройств" выше) перед тем, как самому
затриггерить `LOAD`/`EXTRACT`/и т.д.

В отличие от `mod_load`, `str_copy()` САМ НЕ триггерит никакую команду
устройства - это чистое "скопировать байты"; `poke(..._COMMAND, ...)`,
который реально что-то с ними делает - отдельный, явный шаг (один и тот
же буфер может заполняться и переиспользоваться несколько раз подряд
под разные команды - например `LOAD`, потом несколько раз
`EXTRACT_TILE`). Ошибки на этапе компиляции: массив должен быть
маппированным (обычному, немаппированному массиву некуда осмысленно
копировать байты, предназначенные устройству), и строка должна
помещаться в объявленный размер массива (дозаполняется нулями, если
короче; если длиннее - жёсткая ошибка компиляции, без молчаливого
обрезания).

## #include - подключаемые библиотеки

    #include "STRLIB.MC"

Подключает другой файл исходника Мини-C на этапе компиляции - набор
`const`/функций, которые не хочется перепечатывать в каждую программу,
хранящийся в одном месте. Библиотеки всегда лежат в ФИКСИРОВАННОМ месте
- диск C, папка `DEV/LIB` (реальный файл `C/DEV/LIB/STRLIB.MC` рядом с
исполняемым файлом эмулятора) - независимо от того, с какого диска
реально собирается сама программа; препроцессинг сборки
(`Disk::build()`) всегда ищет их именно там, никогда не в текущей папке
и не на другом диске.

Строка `#include` должна быть ЕДИНСТВЕННЫМ содержимым своей строки
(пробелы вокруг допустимы) - `build` сканирует СЫРОЙ текст исходника на
такие строки ДО того, как за него возьмётся настоящий лексер Мини-C
(`#` больше нигде в языке не является допустимым символом), читает
полный текст названного файла и заменяет строку `#include` на пустую -
поэтому номера строк ОСТАЛЬНОГО кода вашего файла совершенно не
сдвигаются. Текст каждой подключённой библиотеки затем лексуется как
свой независимый чанк со СВОИМ счётчиком строк, начинающимся с 1 (тот
же приём, что и у встроенной прелюдии устройств выше) - синтаксическая
ошибка внутри библиотеки покажет правильный номер строки ВНУТРИ этого
библиотечного файла, а не сдвинутую позицию в вашем.

Библиотечный файл - обычный текст Мини-C (`const`, `int arr[N] =
адрес;`, функции) без собственного `main()` (он никогда не собирается
самостоятельно, только вклеивается в того, кто его подключает).
Сознательные ограничения v1:

- `#include` сканируется ТОЛЬКО в верхнеуровневом файле, переданном в
  `build` - текст самой библиотеки повторно не сканируется, поэтому
  библиотека не может подключить другую библиотеку (не нужно решать
  проблему вложенных/циклических подключений).
- Работает только для сборки `.MC`, не для `.ASM`.
- Отсутствующий/опечатанный файл библиотеки или некорректная строка
  `#include` (без кавычек) проваливает всю сборку (`STATUS=2`, как и
  любая другая ошибка сборки).
- Повторное подключение одной и той же библиотеки (или имени, которое
  случайно совпало с чем-то, объявленным вами самим) - не ошибка, та же
  терпимость "последнее объявление побеждает", что и везде в
  компиляторе (см. "const" выше) - это не include guard, просто
  безобидно по устройству механизма.
- Имя файла библиотеки сопоставляется с сырым текстом исходника до
  того, как появится хоть один настоящий токен Мини-C - оно НЕ проходит
  через 12-байтный протокол `NAME`-регистра `Disk`, как обычные имена
  `.MC`/`.RUN`, поэтому не ограничено форматом 8.3, хотя короткие имена
  всё равно разумная конвенция.

Готовый рабочий пример - `C/DEV/LIB/STRLIB.MC` (маленький хелпер
`print_number3(x, y, value)`) и `C/DEV/SRC/LIBDEMO.MC` (подключает его).

## Чего сознательно нет в v1

- Строковых ЛИТЕРАЛОВ как рантайм-значения - `print_str`/`mod_load`/
  `str_copy` по-прежнему принимают их только как компилируемый в
  фиксированное место текст, никогда как переменную. Рантайм-строки как
  таковые - есть (см. "Тип `string`"), но без сравнения и
  конкатенации - не понадобились единственному потребителю (плейлист
  `PLAYER.MC`), добавлять впрок не стали.
- Указателей, `struct`, `switch`, любой 16-битной арифметики сверх
  того, что сознательно поддерживает `long` (см. "Тип `long`"), 32-бит
  типа нет вовсе.
- Рекурсии (см. "Функции" выше).
- Составных операторов присваивания (`+=` и т.п.) и `++`/`--` -
  писать `i = i + 1;`.

## Пример: COUNTER.MC

Готовый пример - `C/DEMOS/COUNTER.MC`: функция `sum(n)` суммирует
`1..n` в цикле, `main()` печатает результат тремя цифрами через
`poke()` в Text VRAM, используя промежуточный массив `digits[3]` и
`DIV`/`MOD` (тот же приём перевода числа в десятичный текст, что и

    counter

## Пример: SNAKE.MC

`C/DEMOS/SNAKE.MC` - консольная змейка, покрывает почти весь язык
сразу: маппированные массивы (игровое поле, по одному массиву на
строку экрана - см. "Маппированные массивы" выше), обычные массивы
(`snakeX`/`snakeY` - тело змейки, классическое движение сдвигом
массива), функции, `while`/`for`/`if`, прямое чтение клавиатуры через
`peek(0xF0000005)` (регистр `DATA` устройства `Keyboard`, раздел 9) -
БЕЗ прерываний (`EI`/`DI` в мини-C нет и не будет - это опкоды CPU, а
не MMIO-регистр, `poke()` до них не дотягивается; впрочем, `exec`/
`run` и так выполняются с выключенными прерываниями - см. `cmd_exec_run`
в `SHELL.ASM`, - так что прямой опрос `DATA` тут не обходной путь, а
единственно рабочий), и `Clock` для паузы между тиками игры. Управление
- `W`/`A`/`S`/`D`, выход - `Ctrl+Q`. Собрать и запустить:

    build snake.mc
    snake

## Пример: MUSIC2.MC

`C/DEMOS/MUSIC2.MC` проигрывает `SPACE_~1.MOD` (`mod_load()` +
`sound_play()`) и ОДНОВРЕМЕННО рисует живой эквалайзер из 4 столбиков
в графическом режиме (`VideoCard`, `poke(VIDEO_COMMAND, 1)` - MODE_ON)
- по столбику на канал ProTracker, высота читается прямо из новых
регистров `CHANNEL0-3_VOLUME` через маппированный массив
(`int channelVol[4] = 0xF0001069;`). `VideoCard` и `SoundCard` -
независимые устройства со своими потоками (см. оба раздела выше) -
запуск обоих из одной программы на Мини-C не требует ничего особенного.
Выход - `Ctrl+Q`. Собрать и запустить:

    build music2.mc
    music2

## Пример: STRLIB.MC / LIBDEMO.MC

`C/DEV/LIB/STRLIB.MC` - крошечная переиспользуемая библиотека: одна
функция, `print_number3(x, y, value)`, печатающая значение 0-255 тремя
десятичными цифрами (тот же приём разбиения на цифры, что и у

`C/DEV/SRC/LIBDEMO.MC` - минимальный пример `#include`: `#include

    libdemo

## Пример: VIEW.MC / DISKIO.MC

`C/DEV/LIB/DISKIO.MC` - небольшая библиотека обёрток над регистрами
`Disk`, параметризованных `diskId` (0=C, 1=D) - тот же приём
`d_cmd`/`d_status`/`d_data`/`d_set_data`, что уже используется прямо
внутри `C/TOOLS/FM.MC`, вынесенный для новых потребителей (сам `FM.MC`
оставлен как есть - переписывать рабочий код без нужды незачем). Кроме
файловых команд (`OPEN_READ`/`READ_BYTE`/`OPEN_WRITE`/`WRITE_BYTE`/
`CLOSE`) есть `diskio_chdir(diskId)`/`diskio_chdir_up(diskId)` (`CHDIR`/
`CHDIR_UP`, см. "Disk" выше) - нужны `C/TOOLS/PLAYER.MC` для плейлиста,
см. "Плейлист (PLAY.LST)" ниже.
`C/TOOLS/VIEW.MC` - постраничный просмотрщик текстовых файлов поверх
неё и `print_number3()` из `STRLIB.MC`: читает имя файла из `cmdArgs`
(см. "Аргументы командной строки" в разделе "Disk" и "Встроенные
константы регистров устройств" выше) и с какого диска его читать -
через `peek(EXEC_CHILD_DISK)`, затем при каждом перелистывании
страницы заново открывает файл и заново считает переводы строк с
начала, а не хранит весь файл в памяти (массив Мини-C не может быть
больше 255 элементов - см. "Типы и переменные" выше - настоящий
текстовый файл в это не влезет). Управление - `↑`/`↓` - предыдущая/
следующая страница (24 строки на страницу, 25-я строка экрана -
статусная), `Esc` - назад к тому, кто её запустил. `F3` в `C/TOOLS/
FM.MC` (`view_selected_file()`) запускает её с выделенным файлом как
аргументом. Собрать и запустить напрямую:

    build view.mc
    view readme.txt

`F3` из `FM.MC` работает без дополнительной настройки - достаточно
собрать `VIEW.RUN` В ТОЙ ЖЕ папке, что и сама `FM.MC` (`C/TOOLS`) -
резервный поиск `LOAD_CHILD` по месту запуска (см. "LOAD_CHILD" в
разделе "Disk", `Disk::lastExecDir`) найдёт его там независимо от
того, какую папку показывают панели `FM.MC` в момент нажатия `F3` -
никакого копирования `.RUN`-файлов и никакого "положить в корень",
которое надо было бы держать в голове.

## Плейлист (PLAY.LST)

`C/TOOLS/PLAYER.MC` (см. "Звук и музыка" выше) умеет играть не только
один трек, заданный параметром, но и список: `player` без аргументов
ищет рядом с собой (`C/TOOLS/PLAY.LST`) текстовый файл-плейлист и
показывает выбираемый список (стрелки/`Enter`, подсказки внизу - тот же
стиль, что `render_status()` в `FM.MC`).

Формат `PLAY.LST` - один трек на строку, `<ДИСК>/<путь от корня диска>`:

    C/DEMOS/SPACE_~1.MOD
    D/GAMES/SONG.MOD

`<ДИСК>` - буква `C` или `D` (байт `68` = `'D'`, всё остальное трактуется
как `C` - см. `load_mod_from_playlist()`); путь после первого `/` -
СОВСЕМ НЕ разбирается на сегменты и не проверяется через `CHDIR` по
одной папке - копируется как есть в 32-байтный `NAME` `ModLoader`
(`std::filesystem::path::operator/`, которым `ModLoader::load()`
резолвит путь на стороне C++, сам корректно понимает вложенные `/`
внутри одной строки - см. `ModLoader.cpp`). Единственное, что должен
сделать сам `PLAYER.MC` перед загрузкой - убедиться, что `currentDir`
ВЫБРАННОГО диска указывает на КОРЕНЬ (иначе путь в плейлисте резолвился
бы относительно того места, откуда реально запущен `player`, а не от
корня) - достаточно один раз выбрать диск через `MODLOADER_DISK_SELECT`
(см. "ModLoader" выше) и подряд несколько раз послать `CHDIR_UP`
(безопасный no-op в корне, как в DOS - см. "Disk").

До 16 строк, без прокрутки (`PLAYLIST_MAX`/`PLAYLIST_WIDTH` в
`PLAYER.MC`) - лишние строки молча игнорируются, как и хвост слишком
длинной строки за `PLAYLIST_WIDTH` байт. Хранится в `string
playlist[16][36]` (см. "Тип `string`" выше) - именно эта задача и была
поводом добавить `string` в язык: 16 параллельных `int`-массивов + `if`-
каскад (старый приём, см. `SNAKE.MC`) для путей произвольной длины были
бы намного многословнее.

`DISKIO.MC` (см. "Пример: VIEW.MC / DISKIO.MC" ниже) дополнен двумя
обёртками для чтения самого `PLAY.LST` и сброса `currentDir` в корень:
`diskio_chdir(diskId)` (`CHDIR`, заходит в папку, записанную в `NAME`
через `diskio_set_name_char`) и `diskio_chdir_up(diskId)` (`CHDIR_UP`).

Управление во время выбора трека: `↑`/`↓` - перемещение по списку,
`Enter` - играть выбранный (переиспользует тот же визуализатор/цикл
проигрывания, что и режим "один трек"), `Ctrl+Q` - выход из плеера
целиком.

Управление во время проигрывания (см. `play_track_loop()` в
`PLAYER.MC`) - `Ctrl+Q` закрывает плеер целиком в ЛЮБОМ режиме запуска
(и с именем файла параметром, и из плейлиста), `P` - пауза/продолжить.
В режиме плейлиста добавлены ещё три: `Esc` - остановить и вернуться к
списку (`ACTION_MENU`), `←`/`→` - предыдущий/следующий трек
(`ACTION_PREV`/`ACTION_NEXT`) БЕЗ зацикливания на границах списка -
`play_track_loop()` сам проверяет `sel > 0`/`sel < count - 1` ДО
остановки трека, поэтому стрелка на первом/последнем треке молча ничего
не делает, а не прерывает и тут же перезапускает то же самое. В режиме
"один трек" (запуск с именем файла параметром) эти три клавиши не
активны вообще - возвращаться/переключаться некуда, `playlistMode=0` у
`play_track_loop()`.

Прошедшее время трека (`elapsedMin`/`elapsedSec` в `PLAYER.MC`,
формат `мм:сс`) выводится в углу экрана рядом с `Order`/`Row`. Настоящей
длительности MOD-файлы не хранят - секвенсор её не подсчитывает
заранее, а честный подсчёт всё равно был бы приблизительным из-за
`Fxx`-эффектов смены темпа/скорости внутри самой песни (см. "SoundCard"
выше) - поэтому показано только "сколько уже играем", без общей длины.
Копится не по показаниям `Clock` (`CLOCK_LOW`/`CLOCK_HIGH`, см. "Clock"
выше - `wait_ms()` и так использует его для покадрового ожидания, и
сбрасывает при каждом вызове), а приблизительно: 30 кадров цикла
`wait_ms(33)` считаются за одну секунду. Небольшой дрейф (30×33мс=990мс,
не ровно 1000) для секундомера в углу экрана не имеет значения.

### Едущие блоки - живой просмотр паттерна

Под VU-метрами (строки 13-24 экрана, раньше пустовавшие) `PLAYER.MC`
рисует "в духе" классических трекеров окно из 9 строк ТЕКУЩЕГО играющего
паттерна по всем 4 каналам - настоящие ноты/сэмплы/эффекты, не
абстрактная анимация (см. "Регистры запроса ячейки паттерна (PATTERN_*)"
в разделе "SoundCard" выше - вся честная работа там, `PLAYER.MC` только
опрашивает и печатает). Формат ячейки - `"C-3 01 A02"` (нота, hex-номер
сэмпла, hex-эффект+параметр), `"---"` - пустая ячейка (нет ноты).

Курсор "текущая строка" ВСЕГДА на одном и том же месте экрана (средний,
5-й из 9 слотов) - едет не он, а содержимое вокруг: `draw_pattern_view()`
(в `PLAYER.MC`) при каждом изменении `ROW` пересчитывает окно `[ROW-4,
ROW+4]` и перезапрашивает все 36 ячеек (9 строк × 4 канала) заново, а
`draw_pattern_frame()` (фон/рамка/подсветка средней строки) рисуется
только один раз, при старте трека - тот же принцип "не перекрашивать
то, что не изменилось", что уже применён в остальном визуализаторе.
Строки, уехавшие за начало/конец паттерна (`ROW-4 < 0` или
`ROW+4 > 63`), рисуются пустыми - см. ограничение в "Регистры запроса
ячейки паттерна" выше (запрос не выходит за пределы текущего паттерна).

Имена нот (`noteNames[36][4]`, `string` - см. "Тип `string`" выше)
заполняются один раз при старте (`init_note_names()`), в том же порядке,
что и `PERIOD_TABLE` в `SoundCard.cpp`: 3 октавы по 12 полутонов,
классический трекерный формат "Буква, диез-или-дефис, октава"
(`"C-1"`, `"C#1"`, ... `"B-3"`).

## Встроенные инструменты: горячие клавиши FM.MC / EDIT.MC / VIEW.MC

Три готовые программы на Мини-C лежат в `C/TOOLS` и рассчитаны на то,
чтобы собрать их один раз и дальше пользоваться как обычными
инструментами ОС - `build fm.mc` / `build edit.mc` / `build view.mc`,
затем запуск как `fm` / `edit ИМЯ` / `view ИМЯ`.

### FM.MC - файловый менеджер

Двухпанельный файловый менеджер в стиле Norton Commander (полное
обоснование дизайна - в шапке самого `C/TOOLS/FM.MC`: независимый
диск/папка на каждую панель через `sync_disk_to_panel()`, запуск
других программ через `exec_child()` и т.д.). Каждая панель просматри-
вает диск (C или D) независимо, включая обе панели на одном и том же
физическом диске, но в разных папках.

| Клавиша | Действие | Подробности |
|---|---|---|
| `Tab` | переключить активную панель | |
| `Up`/`Down` | переместить выделение | |
| `Enter` | зайти в папку, или запустить выделенный `*.RUN` | через `exec_child()`, "Запуск дочерней программы" |
| `Backspace` | подняться на уровень выше | |
| `F2` | Rename - запрашивает новое имя, предзаполненное текущим | `request_rename()`/`perform_rename()` |
| `F3` | View - открывает выделенный файл в `VIEW.MC` | `view_selected_file()` |
| `F4` | Edit - открывает выделенный файл в `EDIT.MC` (полноэкранный редактор) | `edit_selected_file()` |
| `F5` | Copy выделенного файла | |
| `F6` | Move (копирование + удаление источника) | `do_move()` |
| `F7` | MkDir - создаёт папку в текущей папке активной панели | `request_mkdir()`/`perform_mkdir()` |
| `F8` | Del выделенного файла/пустой папки, после подтверждения Y/N | `request_delete()` |
| `F9` | New - создаёт пустой файл в текущей папке активной панели и сразу открывает его в `EDIT.MC` | `request_newfile()`/`perform_newfile()` |
| `F10` | Build - собирает выделенный `*.MC`/`*.ASM` командой `BUILD` диска, печатает `Build OK`/`Build FAILED: <ошибка>` в строке статуса | `build_selected_file()`; регистронезависимая проверка расширения, использует `Disk::readErrorByte()` |
| `Alt+F1` / `Alt+F2` | сменить диск левой/правой панели (C/D) | `select_disk_left()`/`select_disk_right()` |
| `Ctrl+Q` | выход | |

Пункт `..` появляется наверху списка, если панель не в корне диска -
`Enter` на нём поднимает на уровень вверх, как и `Backspace`; его
нельзя удалить/перенести/скопировать/собрать (`is_dotdot_selected()`).

### EDIT.MC - полноэкранный текстовый редактор

Весь файл держится в памяти - один массив на строку
(`line0[80]..line47[80]`, `MAX_LINES=48`/`MAX_COLS=80`), доступ только
через `get_char(row,col)`/`set_char(row,col,v)`, потому что в Мини-C
нет массивов массивов, а обычный `int`-массив упирается в 255
элементов (см. "Типы и переменные" выше - `EDIT.MC` старше типа
`long` и на него не переписывался). Файл длиннее `MAX_LINES` строк или
со строкой длиннее `MAX_COLS` открывается **усечённым** (статус-бар
показывает `TRUNCATED`), а не тихо теряет данные - сохранение
усечённого буфера требует дополнительного подтверждения Y/N, так как
навсегда отбрасывает то, что не влезло.

| Клавиша | Действие |
|---|---|
| стрелки | движение курсора |
| `Home`/`End` | начало/конец текущей строки |
| `PgUp`/`PgDn` | прокрутка на экран вверх/вниз |
| `Enter` | разбить строку в позиции курсора |
| `Backspace`/`Delete` | удалить символ (на границе строки - слить с соседней) |
| `Ctrl+S` | сохранить |
| `Esc` | выход - при несохранённых правках спрашивает `Y`/`N`/`Esc` (сохранить и выйти / выйти без сохранения / отмена) |

Если названного файла ещё нет, `EDIT.MC` открывает новый пустой буфер
вместо отказа (в отличие от `VIEW.MC`, который в этом случае
отказывается). Запускается из `FM.MC` по `F4`/`F9`, либо напрямую:
`exec edit.mc ИМЯ` / `edit ИМЯ` после однократной сборки.

### VIEW.MC - постраничный просмотрщик текстовых файлов

Не держит файл в памяти - вместо этого заново открывает его и заново
считает переносы строк при каждом перелистывании страницы, поскольку
настоящий текстовый файл не влез бы в 255-элементный массив.
Отказывается открывать несуществующий файл (в отличие от `EDIT.MC`).

| Клавиша | Действие |
|---|---|
| `Up`/`Down` | предыдущая/следующая страница (по 24 строки; 25-я строка экрана - статусная) |
| `Esc` | назад к тому, кто запустил |

Запускается из `FM.MC` по `F3`, либо напрямую: `exec view.mc ИМЯ` /
`view ИМЯ` после однократной сборки. См. "Пример: VIEW.MC / DISKIO.MC"
выше - там про библиотеку `DISKIO.MC`, на которой он построен.

## Шпаргалка

Компактная сводка синтаксиса - без объяснений (они выше, по ссылкам в
последнем столбце).

**Типы и переменные**

| Синтаксис | Смысл | Подробности |
|---|---|---|
| `int x;` | глобальная переменная (даже если написана внутри функции) | "Типы и переменные" |
| `int x = 5;` | переменная с начальным значением (только внутри функции) | "Типы и переменные" |
| `int arr[16];` | массив фиксированного размера, индекс 0-255 | "Типы и переменные" |
| `int arr[16] = 0xF0000007;` | маппированный массив - окно в существующую память по адресу | "Маппированные массивы" |
| `long i;` | 16-битный скаляр (0-65535) - только `=`/`+`/`-` с `int`, сравнения, и как индекс массива | "Тип `long`" |
| `arr[i]` (`i` - `long`) | индекс массива до 65535 вместо обычного потолка в 255 | "Тип `long`" |

**Функции**

| Синтаксис | Смысл |
|---|---|
| `int имя(int a, int b) { ... }` | функция (без рекурсии - параметры это глобальные переменные) |
| `return выражение;` | возврат значения (кладёт в `A`, делает `RET`) |
| `int main() { ... }` | обязательная точка входа |

**Управляющие конструкции**

    if (условие) { ... } else { ... }
    while (условие) { ... }
    for (init; условие; post) { ... }

**Операторы**

| Категория | Операторы |
|---|---|
| Арифметика | `+` `-` `*` `/` `%` |
| Биты | `&` `\|` `^` `~` `<<` `>>` |
| Сравнения | `==` `!=` `<` `>` `<=` `>=` |
| Логика | `&&` `\|\|` (с коротким замыканием) |
| Присваивание | `=` |

**Память и MMIO**

| Синтаксис | Смысл | Подробности |
|---|---|---|
| `poke(адрес, значение)` | записать байт по адресу (адрес - константа времени компиляции) | "poke/peek" |
| `peek(адрес)` | прочитать байт по адресу | "poke/peek" |
| `const ИМЯ = значение;` | именованная константа компиляции, памяти не занимает | "const" |

**Встроенные константы регистров устройств**

Уже объявлены в каждой программе - `KEYBOARD_*`, `CLOCK_*`,

готовые маппированные массивы `pngLoaderName`/`mapLoaderName`/
`matrixLoaderName`/`cmdArgs`. `GPU3D_*` (3D + освещение + математический
сопроцессор) и `PHYS_*` (физический ускоритель) в прелюдии НЕТ - вместо
этого `#include "GEOM3D.MC"`/`#include "PHYS3D.MC"` (см. "#include"
ниже). Полный список - см.
"Встроенные константы регистров устройств (прелюдия)" выше.

**Экран (Text VRAM/TextAttr)**

| Вызов | Что делает |
|---|---|
| `clear_screen()` | очищает текст и цвет |
| `print_char(x, y, ch)` | символ `ch` (0-255, CP866) в ячейку `(x, y)` |
| `print_str(x, y, "текст")` | строковый литерал начиная с `(x, y)`, без переноса |
| `print_string(x, y, arr, i)` | строка `arr[i]` (см. "Тип `string`") - рантайм-аналог `print_str` |

**Дочерние программы**

    poke(EXEC_CHILD_DISK, diskId);   // 0=C, 1=D
    exec_child();                    // запустить *.RUN из NAME диска diskId, вернётся после его RET

    cmdArgs[0] = 65; poke(CMD_ARGS_LEN, 1);   // необязательно: передать аргумент (или str_copy(cmdArgs, "..."))

См. "Запуск дочерней программы: exec_child()" выше - до 5 уровней
вложенности, обнуляет `lastKey` перед запуском, диск и имя файла в
`NAME` подготавливает вызывающий код заранее; `cmdArgs`/`CMD_ARGS_LEN`
- заполнить самому, если дочерняя программа принимает аргумент (см.
"Аргументы командной строки" в разделе "Disk").

**Звук и музыка**

| Вызов | Что делает |
|---|---|
| `mod_load("name.mod")` | грузит `.mod`-файл в `SoundCard`, возвращает `STATUS` |
| `sound_play()` / `sound_stop()` | старт/стоп воспроизведения |
| `sound_pause()` / `sound_resume()` | пауза/возобновление без сброса позиции |
| `sound_set_volume(v)` | общая громкость, 0-255 |

См. "Звук и музыка: mod_load()/sound_*()" выше.

**str_copy()**

    str_copy(arr, "текст");   // arr должен быть маппированным массивом - int arr[N] = адрес;

Копирует строковый литерал в маппированный массив на этапе компиляции,
дозаполняя нулями до размера массива, без триггера команды устройства -
см. "str_copy() - копирование строкового литерала в маппированный
массив" выше.

**#include**

    #include "ИМЯ.MC"

Подключает библиотечный файл с диска C, `DEV/LIB`, на этапе компиляции
- см. "#include - подключаемые библиотеки" выше.

**Комментарии**

    // однострочный комментарий до конца строки

**Чего нет в v1**

- Строк как типа (только как литерал в `print_str`/`mod_load`/
  `str_copy`, каждый копирует его в фиксированное место назначения на
  этапе компиляции - никогда не как рантайм-значение, которое можно
  передавать дальше).
- Указателей, `struct`, `switch`, любой 16-битной арифметики сверх
  того, что сознательно поддерживает `long` (см. "Тип `long`"), 32-бит
  типа нет вовсе.
- Рекурсии.
- `+=`/`-=`/... и `++`/`--` - писать `i = i + 1;`.

**Где искать примеры**: `C/DEMOS/COUNTER.MC` (функция, `DIV`/`MOD`,
вывод числа), `C/DEMOS/SNAKE.MC` (массивы, маппированные массивы,
клавиатура, `Clock`), `C/TOOLS/FM.MC` (файловый менеджер, `exec_child()`,
работа с диском напрямую через `poke`/`peek`), `C/DEMOS/MUSIC2.MC`
(`mod_load()`/`sound_*()`, графический режим одновременно со звуком,
маппированный массив поверх регистров визуализации `SoundCard`),
`C/DEV/LIB/STRLIB.MC` + `C/DEV/SRC/LIBDEMO.MC` (`#include`,
переиспользуемая библиотечная функция), `C/DEV/LIB/DISKIO.MC` +
`C/TOOLS/VIEW.MC` (чтение файла напрямую через протокол `Disk`,
аргументы командной строки через `cmdArgs`, запуск через
`exec_child()` из `F3` в `C/TOOLS/FM.MC`).
